How to read it

  1. Apple answers with a POST, not a redirect. That's why the login cookie must be SameSite=None: a Lax cookie is not sent on a cross-site POST.
  2. The client secret isn't a fixed string: TiffinBox signs a short JWT with its .p8 key.
  3. The ID token is the only signed answer. The email comes from it; the user field is just a display name.
  4. The three yellow boxes are where most Apple logins break.

2. Data flow: first vs second sign-in

Rahul signs in twice. Watch the user field: it only exists the first time.

sequenceDiagram
    autonumber
    actor R as Rahul's browser
    participant T as TiffinBox
    participant A as Apple

    R->>T: GET /login/apple
    T-->>R: 302 to Apple, cookie apple_login (SameSite=None, Secure)
    R->>A: authorize, scope name email, response_mode form_post, state, nonce
    A-->>R: Face ID, then an auto-submitting form
    R->>T: POST /callback/apple code, state, user = Rahul Sharma (FIRST TIME ONLY)
    T->>A: POST /auth/token code + client_secret JWT (ES256, kid, iss = team, sub = Services ID)
    A-->>T: id_token (sub 001234.5f2c..., email, email_verified "true"), refresh_token
    T->>T: verify id_token, create acct_5K4XQQ, SAVE name, store refresh_token
    T-->>R: 303 /me, tb_sid (HttpOnly, SameSite=Lax)
    Note over R,A: a week later, the same steps again
    R->>T: POST /callback/apple code, state (no user field)
    T->>A: POST /auth/token
    A-->>T: id_token (same sub)
    T->>T: same sub, so the same acct_5K4XQQ, the name is already saved
    T-->>R: 303 /me

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Step 5: the name arrives once. If step 8 fails, it is lost.
  3. Step 6: the client secret is a JWT TiffinBox made itself.
  4. Steps 10 to 14: no name this time. The sub finds the same account.

3. iPhone, notifications, deletion

Three more ways Apple talks to your backend.

sequenceDiagram
    autonumber
    participant I as iPhone app
    participant T as TiffinBox
    participant A as Apple

    I->>I: rawNonce, nonce = SHA256(rawNonce)
    I->>A: Face ID with nonce
    A-->>I: identityToken, authorizationCode
    I->>T: POST /auth/apple/native identityToken, code, rawNonce
    T->>T: verify, aud = bundle id, nonce = SHA256(rawNonce)
    T->>A: redeem code (client secret, sub = bundle id)
    A-->>T: refresh_token, same sub as the website
    T-->>I: 200, same account acct_5K4XQQ

sequenceDiagram
    autonumber
    actor U as User
    participant A as Apple
    participant T as TiffinBox

    U->>A: Settings, Stop using Apple ID with TiffinBox
    A->>T: POST /apple/notifications payload = signed JWT
    T->>T: verify JWT, events type consent-revoked
    T->>T: end all sessions, drop Apple tokens
    T-->>A: 200
    U->>T: DELETE /me in the app
    T->>A: POST /auth/revoke refresh_token
    A-->>T: 200, TiffinBox removed from the Apple ID
    T-->>U: deleted

Left: the iPhone app never shows a web page; the backend checks the same ID token, but with the bundle ID as aud and a hashed nonce. Right: Apple pushes changes to you (email-disabled, email-enabled, consent-revoked, account-delete), and you call revoke when the user deletes their account.

Diagrams are drawn with Mermaid, which loads from the internet the first time you open this page.
