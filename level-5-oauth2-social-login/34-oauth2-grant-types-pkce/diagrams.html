2. Data flow: PKCE

A malicious app on Rahul's phone grabs the code on its way back. It still can't get a token.

sequenceDiagram
    autonumber
    participant APP as PrintKaro mobile app
    participant B as Phone browser
    participant AS as Authorization server
    actor EVIL as Malicious app on the same phone

    APP->>APP: verifier = 64 random chars (kept in memory)
    APP->>APP: challenge = BASE64URL(SHA256(verifier)) = KJPhqd...
    APP->>B: open /authorize?client_id=printkaro-mobile, code_challenge=KJPhqd..., method S256
    B->>AS: GET /authorize (Rahul is logged in)
    AS->>AS: save challenge KJPhqd... with the new code
    AS-->>B: 302 to printkaro callback?code=_i9SAs...&state=s1
    B-->>EVIL: the same callback scheme is claimed by EVIL, it gets the code
    EVIL->>AS: POST /token code=_i9SAs..., no verifier
    AS-->>EVIL: 400 code_verifier is missing
    EVIL->>AS: POST /token code=_i9SAs..., verifier = a guess
    AS->>AS: hash of the guess is not KJPhqd..., burn the code
    AS-->>EVIL: 400 PKCE verification failed
    Note over APP,AS: the real app simply starts a new login, with a NEW verifier
    APP->>AS: POST /token new code + the real verifier
    AS-->>APP: 200 access_token + refresh_token

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–3: only the hash leaves the app. The verifier never travels until the token request.
  3. Steps 4–7: the code goes back through the phone's browser and OS, where another app can grab it.
  4. Steps 8–12: without the verifier the code is useless, and a wrong guess burns it.
  5. Steps 13–14: the real app has the verifier, so it gets the tokens.

3. Data flow: device code

The PhotoVault TV app has no keyboard. Rahul approves it on his phone while the TV waits.

sequenceDiagram
    autonumber
    participant TV as PhotoVault TV app
    participant AS as Authorization server
    actor P as Rahul's phone

    TV->>AS: POST /device_authorization client_id=photovault-tv, scope=photos.read
    AS-->>TV: device_code (secret), user_code PPSM-JNQW, verification_uri, interval 5
    TV->>TV: show "Open localhost:3000/device and enter PPSM-JNQW" (and a QR code)
    TV->>AS: POST /token grant_type=device_code
    AS-->>TV: authorization_pending
    TV->>AS: POST /token again, too soon
    AS-->>TV: slow_down (interval is now 10 s)
    P->>AS: log in, enter ppsm-jnqw, Allow
    AS-->>P: Done! Your TV is now connected
    TV->>AS: POST /token after 10 s
    AS-->>TV: access_token + refresh_token for u_rahul
    TV->>AS: POST /token once more
    AS-->>TV: invalid_grant (the device_code worked once)

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–3: the TV gets two codes. The long device_code stays secret on the TV; the short user_code is shown to the human.
  3. Steps 4–7: the TV polls, and must respect interval and slow_down.
  4. Steps 8–9: Rahul approves on a device with a real browser. The TV never sees his password.
  5. Steps 10–13: the next poll returns tokens, once.
