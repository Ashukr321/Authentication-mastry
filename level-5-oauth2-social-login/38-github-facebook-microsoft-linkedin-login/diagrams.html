How to read it

  1. The start and the state check are the same for every provider. The pending login also remembers the provider, which stops mix-up attacks.
  2. Only the middle row is provider-specific: each adapter knows its provider's endpoints and quirks.
  3. Every adapter returns the same shape, so the rest of the app never asks "which provider?".
  4. The yellow box is the rule that matters most: the account key is the provider's permanent id.

2. Data flow: nOAuth

Vikram makes his own Microsoft tenant and sets his email to Rahul's. What happens depends on how the app finds accounts.

sequenceDiagram
    autonumber
    actor V as Vikram
    participant MS as Microsoft (his own tenant)
    participant APP as An app

    V->>MS: create tenant fabrikam, set user email = Rahul's email
    V->>APP: Log in with Microsoft
    APP->>MS: authorize, then token
    MS-->>APP: ID token, tid f00dcafe..., oid ...0666, email = Rahul's email (not verified)
    alt app finds users BY EMAIL
        APP->>APP: Rahul's email belongs to Rahul's account
        APP-->>V: logged in as RAHUL (account takeover)
    else app finds users by tid + oid (PrintKaro)
        APP->>APP: f00dcafe... + ...0666 is a new identity
        APP-->>V: logged in to his OWN new account acct_TLFzwg
    else app allow-lists tenants
        APP->>APP: tenant f00dcafe... is not allowed
        APP-->>V: 400 login failed
    end

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–4: everything is real and correctly signed. Microsoft is not hacked; the email claim was simply never meant to be an identity.
  3. First branch: an app that matches by email hands Vikram Rahul's account.
  4. Second branch: keying by tid + oid gives Vikram an account of his own, which is harmless.
  5. Third branch: an internal company app should only accept its own tenant id.
