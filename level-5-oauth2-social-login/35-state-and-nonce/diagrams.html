1. Flow diagram

What PrintKaro's callback checks, in order. Each red exit is one attack stopped.

Logged in Refused The two checks this topic is about 
flowchart TD
    S(["GET /login"]) --> G["new random state + nonce,<br/>saved in THIS browser's session<br/>with returnTo, 10 min expiry"]
    G --> AZ["redirect to /authorize<br/>?state=...&nonce=..."]
    AZ --> CB(["GET /callback?code=...&state=..."])
    CB --> ST{"state in this session,<br/>not expired?<br/>(then delete it)"}
    ST -- "No: someone else's login,<br/>or a replay" --> X1[/"400 state mismatch<br/>stops login CSRF"/]
    ST -- Yes --> T["POST /token with the code"]
    T --> V{"ID token valid?<br/>alg, signature, iss, aud, exp"}
    V -- No --> X2[/"400 invalid ID token"/]
    V -- Yes --> N{"id_token.nonce ==<br/>this session's nonce?"}
    N -- "No: a code from a<br/>different login" --> X3[/"400 nonce mismatch<br/>stops code injection"/]
    N -- Yes --> OK[/"✅ logged in, NEW session id,<br/>redirect to the saved returnTo"/]

How to read it

  1. Both values are made fresh for every login and stored on the server, next to this browser's session.
  2. state is checked first, from the URL. The provider never checks it; only the client can.
  3. nonce is checked last, from inside the ID token, and only after the token itself is verified.
  4. returnTo comes from the session, never from the callback URL.

2. Data flow: login CSRF

Vikram's login, finished in Rahul's browser. state is what notices.

sequenceDiagram
    autonumber
    actor V as Vikram's browser
    actor R as Rahul's browser
    participant PK as PrintKaro (client)
    participant AS as PhotoVault Accounts

    V->>PK: GET /login
    PK->>PK: Vikram's session gets state HnKS...
    PK-->>V: redirect to /authorize?state=HnKS...
    V->>AS: authorize, logged in as vikram
    AS-->>V: redirect to /callback?code=XHEt...&state=HnKS...
    Note over V: Vikram does NOT open it. He sends the link to Rahul.
    V->>R: see the photos I printed for you!
    R->>PK: GET /callback?code=XHEt...&state=HnKS...
    alt naive callback, no state check
        PK->>AS: POST /token code=XHEt...
        AS-->>PK: ID token, sub u_vikram
        PK-->>R: logged in as u_vikram
        Note over R,PK: Rahul's card, address and photos now go into Vikram's account
    else safe callback
        PK->>PK: Rahul's session has no state HnKS...
        PK-->>R: 400 state mismatch, not logged in
    end

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–5: a perfectly normal login, for Vikram's account.
  3. Steps 6–7: the unused callback URL is the weapon. A link, a hidden image or an auto-submitting page will do.
  4. The alt box: without a state check, PrintKaro happily finishes Vikram's login in Rahul's browser. With it, Rahul's session never started that login, so it's refused before the code is even used.

3. Data flow: code injection

Rahul's code, used in Vikram's browser with Vikram's own valid state. Only nonce (or PKCE) notices.

sequenceDiagram
    autonumber
    actor R as Rahul's browser
    actor V as Vikram's browser
    participant PK as PrintKaro (client)
    participant AS as PhotoVault Accounts

    R->>PK: GET /login
    PK->>PK: Rahul's session gets state dqo4..., nonce d-WZ...
    R->>AS: authorize, logged in as rahul, nonce d-WZ...
    AS-->>R: redirect to /callback?code=dnkT...&state=dqo4...
    Note over R,V: a malicious extension sends this URL to Vikram before Rahul's browser uses it
    V->>PK: GET /login (just to get his OWN state)
    PK->>PK: Vikram's session gets state fsbf..., nonce of his own
    V->>PK: GET /callback?code=dnkT... (Rahul's) &state=fsbf... (Vikram's)
    PK->>PK: state fsbf... is in Vikram's session, the check PASSES
    PK->>AS: POST /token code=dnkT...
    AS-->>PK: ID token, sub u_rahul, nonce d-WZ...
    alt no-nonce callback
        PK-->>V: logged in as u_rahul
    else safe callback
        PK->>PK: nonce d-WZ... is not Vikram's session nonce
        PK-->>V: 400 nonce mismatch, not logged in
    end

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–4: Rahul's normal login. The nonce goes into the code's record at PhotoVault.
  3. Steps 5–9: Vikram pairs Rahul's code with his own state, so the state check can't help.
  4. Steps 10–11: the ID token carries Rahul's nonce, inside the signature.
  5. The alt box: comparing that nonce with the session's nonce is what catches it. PKCE would also stop it, at /token.
