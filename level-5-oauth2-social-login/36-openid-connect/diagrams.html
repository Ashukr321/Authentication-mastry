1. Flow diagram

What PrintKaro does with the token response, from the ID token to a logged-in account.

Logged in Login refused Where beginners slip 
flowchart TD
    A(["token response:<br/>access_token + id_token"]) --> K["read kid from the header<br/>(decode only, trust nothing yet)"]
    K --> J{"kid in the cached JWKS?"}
    J -- No --> RF["refetch JWKS once,<br/>from the DISCOVERED jwks_uri"]
    RF --> J2{"found now?"}
    J2 -- No --> X[/"login refused<br/>+ log the reason"/]
    J -- Yes --> V
    J2 -- Yes --> V{"jwt.verify: RS256 pinned,<br/>signature, iss, aud = printkaro,<br/>exp (± 30 s)"}
    V -- No --> X
    V -- Yes --> N{"nonce = this session's nonce?"}
    N -- No --> X
    N -- Yes --> U{"optional /userinfo<br/>with the ACCESS token:<br/>same sub?"}
    U -- No --> X
    U -- Yes --> F{"account with<br/>iss + sub exists?"}
    F -- "Yes: returning user" --> OK[/"✅ update the profile copy,<br/>new session id"/]
    F -- "No: first login" --> NEW["create account keyed by iss + sub<br/>(NOT by email)"]
    NEW --> OK

How to read it

  1. Decoding is only used to find the kid. Nothing in the token is trusted until jwt.verify passes.
  2. Keys come only from the jwks_uri found by discovery, never from a URL inside the token.
  3. The aud check is what makes this login: the token was made for PrintKaro, not for some other app.
  4. The account is found by iss + sub. Email and name are just a copy that gets refreshed.

2. Data flow

Rahul clicks "Log in with PhotoVault" on PrintKaro. Discovery, JWKS and userinfo are the parts OIDC adds to OAuth.

sequenceDiagram
    autonumber
    actor B as Rahul's browser
    participant RP as PrintKaro (relying party)
    participant OP as PhotoVault (OpenID provider)

    RP->>OP: GET /.well-known/openid-configuration
    OP-->>RP: issuer, authorization_endpoint, token_endpoint, userinfo_endpoint, jwks_uri
    B->>RP: GET /login
    RP->>RP: save state, nonce, PKCE verifier in the session
    RP-->>B: redirect to /authorize?scope=openid profile email, state, nonce, code_challenge
    B->>OP: authorize (Rahul logs in at PhotoVault)
    OP-->>B: redirect to /callback?code=NKJS...&state=kz1T...
    B->>RP: GET /callback?code=NKJS...&state=kz1T...
    RP->>OP: POST /token code + client secret + code_verifier
    OP-->>RP: access_token + id_token (RS256, kid pv-9b--Fct_)
    RP->>OP: GET /jwks.json (first time, or unknown kid)
    OP-->>RP: public key pv-9b--Fct_
    RP->>RP: verify id_token, check iss, aud, exp, nonce
    RP->>OP: GET /userinfo (Bearer access_token)
    OP-->>RP: sub 248289761001, name, email, email_verified
    RP->>RP: same sub, find account by iss + sub (acct_-5UyaA)
    RP-->>B: 303 to /me with a NEW session cookie

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2: discovery. PrintKaro only knows PhotoVault's issuer URL; everything else comes from here.
  3. Steps 3–10: the OAuth code flow from topics 33–35, with openid in the scope, so the token response also has an id_token.
  4. Steps 11–13: the public key from JWKS verifies the ID token.
  5. Steps 14–16: /userinfo is optional. It takes the access token, and its sub must match.
  6. Step 17: from now on, PrintKaro's own session keeps Rahul logged in.

3. ID token vs access token

One response, two tokens, two different readers.

Right use Wrong use 
flowchart TD
    I(["ID token (always a JWT)"]) --> I1["aud = printkaro (the APP)<br/>iss, sub, exp, iat,<br/>auth_time, nonce, email..."]
    I1 --> I2[/"PrintKaro verifies it once,<br/>then starts its own session"/]
    I1 -. "sent to an API" .-> I3[/"wrong: aud is not the API"/]

    T(["Access token (any format)"]) --> T1["for an API, scopes<br/>openid profile email"]

    T1 -. "used as proof of login" .-> T3[/"wrong: token substitution,<br/>it may be meant for another app"/]

The ID token answers who logged in, for this app. The access token answers what may be done at an API. After login, neither replaces your own session.
