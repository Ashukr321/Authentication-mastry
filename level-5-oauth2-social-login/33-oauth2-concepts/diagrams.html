1. Flow diagram

The checks along the authorization code flow, from PrintKaro's "Import" button to the photos.

Success Refused Where beginners slip 
flowchart TD
    A(["Rahul clicks Import from PhotoVault"]) --> AZ["PrintKaro stores a random state,<br/>redirects the browser to /authorize"]
    AZ --> R{"client_id known AND<br/>redirect_uri registered EXACTLY?"}
    R -- No --> E1[/"Error page on PhotoVault,<br/>NO redirect"/]
    R -- Yes --> S{"scopes allowed<br/>for this client?"}
    S -- No --> E2[/"back to the app:<br/>error=invalid_scope"/]
    S -- Yes --> L["Rahul logs in ON PhotoVault's page,<br/>sees the consent screen"]
    L --> D{"Allow?"}
    D -- Deny --> E3[/"back to the app:<br/>error=access_denied"/]
    D -- Allow --> C["code: random, 60 s, one use,<br/>tied to client + redirect_uri"]
    C --> ST{"PrintKaro: state matches?"}
    ST -- No --> E4[/"stop: not started here"/]
    ST -- Yes --> T{"POST /token: client secret OK,<br/>code valid, unused, same redirect_uri?"}
    T -- No --> E5[/"invalid_client / invalid_grant<br/>(reused code: revoke its token)"/]
    T -- Yes --> TK["access_token (10 min, photos.read)<br/>kept on PrintKaro's SERVER"]
    TK --> API{"API: token valid AND<br/>has the scope?"}
    API -- "No token / expired" --> E6[/"401 invalid_token"/]
    API -- "Wrong scope (delete)" --> E7[/"403 insufficient_scope"/]
    API -- Yes --> OK[/"✅ Rahul's photos only"/]

How to read it

  1. The redirect URI check comes first, and a bad one is never redirected to: that's where the code would leak.
  2. The password is typed only on PhotoVault's page. PrintKaro never sees it.
  3. The code is weak on purpose (it travels through the browser), so it's short-lived, one-use and needs the client secret.
  4. The state check (topic 35) stops someone else's code being pushed into Rahul's session.
  5. The API checks the token and then the scope. PrintKaro asked for read only, so delete fails.

2. Data flow

The full authorization code flow with the real requests from the demo. Watch which arrows go through the browser.

sequenceDiagram
    autonumber
    actor B as Rahul's browser
    participant PK as PrintKaro server (client, :3000)
    participant AS as PhotoVault Accounts (auth server, :3001)
    participant API as PhotoVault API (resource server, :3002)

    B->>PK: GET /connect
    PK->>PK: save state=sdecQ1pM in Rahul's PrintKaro session
    PK-->>B: 302 to :3001/authorize?response_type=code, client_id=printkaro, redirect_uri=:3000/callback, scope=photos.read, state=sdecQ1pM
    B->>AS: GET /authorize?...
    AS-->>B: PhotoVault login page
    B->>AS: POST /login rahul + password
    AS-->>B: consent page, PrintKaro wants to See your photos
    B->>AS: POST /consent Allow
    AS-->>B: 303 to :3000/callback?code=aIu08o...&state=sdecQ1pM
    B->>PK: GET /callback?code=aIu08o...&state=sdecQ1pM
    PK->>PK: state matches the saved one
    PK->>AS: POST /token (Basic printkaro:secret) grant_type=authorization_code, code, redirect_uri
    AS-->>PK: access_token ctawzC..., Bearer, expires_in 600, scope photos.read
    PK->>API: GET /photos, Authorization Bearer ctawzC...
    API-->>PK: Rahul's 3 photos
    PK-->>B: page with Goa beach sunset, Dadi's 80th birthday, Diwali rangoli
    Note over B,API: the browser saw the code but never the token, and PrintKaro never saw the password

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–4: the front channel. PrintKaro can only send the browser to PhotoVault with a URL.
  3. Steps 5–9: login and consent happen entirely between the browser and PhotoVault.
  4. Steps 10–11: the code comes back through the browser, and PrintKaro checks state.
  5. Steps 12–13: the back channel. PrintKaro's server proves who it is with its secret and gets the token.
  6. Steps 14–16: the token is used on the API. The browser only ever gets HTML.

The four OAuth roles, and which messages go through the browser (front channel) or directly between servers (back channel).
