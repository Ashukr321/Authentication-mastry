How to read it

  1. Green boxes are the protocol work from topics 33 to 36. The library does them.
  2. Yellow boxes are still yours: mapping the provider's user to your account, authorization, and configuration.
  3. The dotted lines: your settings shape how the library behaves (wrong secret, insecure cookies or a trusted Host header undo its protection).

2. Data flow: Auth.js sign-in

The CSRF token, the cookies, and where your callbacks run. Values are from the demo.

sequenceDiagram
    autonumber
    actor R as Rahul's browser
    participant A as Auth.js at /auth
    participant K as KaroID
    participant Y as Your callbacks

    R->>A: GET /auth/csrf
    A-->>R: csrfToken 99bc12..., cookie authjs.csrf-token = token + hash
    R->>A: POST /auth/signin/karoid csrfToken=99bc12... callbackUrl=/authjs/me
    A->>A: token matches the cookie? callbackUrl same site?
    A-->>R: 302 to KaroID with state, nonce, code_challenge, cookies for pkce/state/nonce
    R->>K: authorize, Continue as rahul
    K-->>R: 302 /auth/callback/karoid?code=rQkG...&state=...
    R->>A: GET /auth/callback/karoid (with the pkce/state/nonce cookies)
    A->>K: POST /token code + code_verifier (client_secret_basic)
    K-->>A: id_token (sub kr_7Hq2LmV9), access_token
    A->>A: verify id_token: JWKS, iss, aud, exp, nonce
    A->>Y: jwt callback with account + profile
    Y-->>A: token.appUserId = acct_5gLc7A
    A-->>R: 302 /authjs/me, cookie authjs.session-token (encrypted JWE, 30 days)
    R->>A: GET /auth/session
    A->>Y: session callback
    A-->>R: user id acct_5gLc7A, name Rahul Sharma

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1 to 4: sign-in is a POST with a CSRF token checked against a cookie, so another site can't start it.
  3. Steps 9 to 11: the protocol checks, all inside the library.
  4. Steps 12 and 13: your code. This is where the provider's user becomes your account.
  5. Step 14: with the default JWT strategy the session itself is in the cookie, encrypted with AUTH_SECRET.

3. Passport's moving parts

Left: logging in once. Right: every request after that.

flowchart TD
    L(["GET /passport/callback"]) --> S["Strategy (openid-client)<br/>code + PKCE, verify ID token"]
    S --> V["verify(tokens, verified)<br/>YOUR findOrCreateUser"]
    V --> LI["req.login: regenerate session id"]
    LI --> SE["serializeUser: store user.id<br/>in the session"]
    SE --> ST[("session store<br/>MemoryStore in the demo,<br/>Redis in production")]

flowchart TD
    Q(["any request, cookie pk.sid"]) --> SS["express-session<br/>load the session"]
    SS --> D["deserializeUser(id)<br/>YOUR user lookup"]
    D --> U["req.user, req.isAuthenticated()"]
    U --> R["your route"]
    O(["POST /passport/logout"]) --> LO["req.logout(callback)<br/>clears user, regenerates session"]

Passport gives you the pieces, not the whole house: you choose the strategy, write verify and deserializeUser, pick the session store and the cookie flags. Auth.js and Spring Security come with more of this already built.
