How to read it

  1. Left, sending: four limits run before any code is made: valid input, per-IP, per-destination failures, and the 60-second resend timer.
  2. Only an HMAC of the code is stored, never the code itself.
  3. Right, checking: the attempt counter goes up before the compare, so parallel guesses can't sneak past the limit.
  4. Two limits work together: 5 tries per code and 10 failures per email/phone per hour.
  5. The yellow boxes are where guessing gets counted or a code gets destroyed.

2. Data flow

Priya signs in to PrintKaro on her laptop with a code sent to her phone.

sequenceDiagram
    autonumber
    actor P as Priya
    participant B as Laptop browser
    participant S as PrintKaro server
    participant DB as Database
    participant T as SMS provider
    participant Ph as Priya's phone

    P->>B: Picks SMS, types "+91 98765-43210"
    B->>S: POST /auth/otp/request { channel: "sms", to: "+91 98765-43210" }
    Note over S: normalize → "+919876543210" (+91 allowed)<br/>IP limit OK, no code in the last 60 s
    Note over S: code = randomInt(0, 1000000) → "272625"<br/>challengeId = randomBytes(32) → "tv1b…aQM"
    S->>DB: INSERT challenge { id: "tv1b…", codeHash: HMAC(secret, "tv1b…:272625"), attempts: 0, expiresAt: +5 min }
    S->>T: send to +919876543210: "272625 is your PrintKaro code…" + "@printkaro.in #272625"
    T->>Ph: SMS arrives
    S-->>B: 202 { challengeId: "tv1b…", expiresInSeconds: 300 }
    Ph-->>P: Reads 272625 (or the browser offers to autofill it)
    P->>B: Types the code into the one-time-code box
    B->>S: POST /auth/otp/verify { challengeId: "tv1b…", code: "272625" }
    S->>DB: attempts = attempts + 1 → 1 (of 5)
    Note over S: timingSafeEqual(HMAC(secret, "tv1b…:272625"), codeHash) ✓
    S->>DB: DELETE challenge "tv1b…", reset failures for this phone
    S->>DB: Find or INSERT user { id: "u_7", phone: "+919876543210" }
    S->>DB: INSERT session { sha256(sid), userId: "u_7", expiresAt: +7 days }
    S-->>B: 200 { message: "Signed in", isNewUser: true } + Set-Cookie: sid=1FV6… (HttpOnly, SameSite=Lax)

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Step 3: the phone number is normalized first, so every format of it shares one set of limits.
  3. Step 5: the database gets only the HMAC. The plain code goes only into the SMS (step 6).
  4. Step 8: the browser gets the challengeId, not the code. The code travels a different path: through Priya's phone and her eyes.
  5. Step 12: the attempt is counted before the compare in step 13. Step 14: the code is deleted, so it works once.

The last SMS line @printkaro.in #272625 lets the phone autofill the code only on printkaro.in, not on a look-alike phishing site.

3. Brute force math: why limits matter

An attacker scripts guesses against Rahul's phone number. Same 6-digit code, three servers.

Broken Weak Safe enough 
flowchart LR
    A(["Attacker script:<br/>guess 000000, 000001, …"]) --> N["No limits"]
    A --> P["5 tries per code only"]
    A --> Q["5 tries per code<br/>+ 10 fails per phone per hour"]
    N --> N2[/"1,000,000 guesses<br/>a few minutes: account taken"/]
    P --> P2[/"New code every minute,<br/>5 guesses each: 7,200 a day<br/>about 1 in 140 per day"/]

How to read it

  1. Red: with no limits, a 6-digit code is a 6-digit password anyone can try a million times.
  2. Yellow: a per-code limit alone is not enough: the attacker just asks for a new code every minute.
  3. Green: adding a cap per email/phone cuts it to about 240 guesses a day, and the flood of unwanted codes warns the real owner.

Want even safer? Lock the account for review after repeated lockouts, use 8 digits for payments, or move to TOTP (topic 44) and passkeys (topic 46).
