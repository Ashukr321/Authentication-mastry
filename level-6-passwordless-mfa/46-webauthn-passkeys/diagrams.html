1. Server checks

What POST /register/verify and POST /login/verify check, in order. Both share the first part; login ends with the signature.

How to read it

  1. The challenge is deleted the first time it's seen, even if a later check fails. One challenge, one try.
  2. The two yellow checks tie the response to our site: the origin the browser wrote, and the RP ID the authenticator signed for.
  3. UV means a fingerprint, face or PIN was checked. That's why a passkey login counts as MFA.
  4. Registration ends by saving the public key. Login ends by using it to check the signature.
  5. Synced passkeys always send signCount: 0, so the clone check only runs when a counter is in use.

2. Data flow

Rahul signs up for PrintKaro with only a passkey, then signs in again the next day. The private key never leaves his phone.

sequenceDiagram
    autonumber
    actor U as Rahul
    participant B as Browser
    participant A as Phone authenticator
    participant S as PrintKaro server
    participant DB as Database

    Note over U,DB: Sign up (registration ceremony)
    B->>S: POST /register/options { email: rahul, name: Rahul Sharma }
    S->>DB: save challenge 79kk... (5 min, single use)
    S-->>B: { challenge, rp: { id: localhost }, user: { id: aZXF... random }, alg -7 or -257 }
    B->>B: rp.id fits this page's domain? ✓ write clientDataJSON with the REAL origin
    B->>A: create a key pair for localhost
    A->>U: Touch the fingerprint sensor
    U-->>A: 👆
    A->>A: new key pair, private key stays inside
    A-->>B: attestationObject { authData: rpIdHash, flags UP UV AT, public key }
    B->>S: POST /register/verify { id: g7Nq..., clientDataJSON, attestationObject }
    S->>DB: delete challenge, check type, origin, rpIdHash, flags
    S->>DB: INSERT user, INSERT credential { id: g7Nq..., public key, signCount: 0 }
    S-->>B: 201 Account created + sid cookie (HttpOnly)
    Note over U,DB: Next day: sign in (authentication ceremony)
    B->>S: POST /login/options (no email)
    S-->>B: { challenge: 03PD..., rpId: localhost, allowCredentials: [] }
    B->>A: sign this for localhost
    A->>U: Sign in as Rahul Sharma? 👆
    U-->>A: 👆
    A-->>B: authenticatorData (counter 1) + signature + userHandle aZXF...
    B->>S: POST /login/verify { id: g7Nq..., clientDataJSON, authenticatorData, signature }
    S->>DB: find credential g7Nq... → public key, owner Rahul
    S->>S: verify(authData + sha256(clientDataJSON), signature, public key) ✓ counter 1 > 0 ✓
    S-->>B: 200 Signed in as Rahul + new sid cookie

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Step 4: the browser, not the website, writes the origin into clientDataJSON.
  3. Steps 6–8: the fingerprint only unlocks the authenticator. It's never sent anywhere.
  4. Step 12: the database stores a public key. A database leak lets nobody log in.
  5. Steps 14–18: login needs no email: the phone knows which passkeys it has for this site.
  6. Step 22: the signature covers the challenge and the origin, so it can't be reused or relayed from another site.

The fingerprint never reaches the server. "Biometric login" with passkeys means the biometric unlocks a key on the device.

3. Why phishing fails

Rahul clicks a link to printkaro-login.in, a perfect copy of PrintKaro. With a password and an OTP he'd lose his account. With a passkey:

Works Blocked The attacker's move

    A(["Rahul on the REAL site<br/>origin: printkaro.com"]) --> B["Site asks for a passkey<br/>rpId: printkaro.com"]
    B --> C{"Browser: is printkaro.com<br/>this page's domain?"}
    C -- Yes --> D["Phone has a passkey for<br/>printkaro.com: 👆 sign"]

How to read it

  1. On the real site, three things agree: the page's domain, the passkey's RP ID, and the origin the server expects.
  2. On the fake site, every path is blocked by a machine check. Rahul doesn't need to notice the wrong domain.
  3. Compare with a password + OTP: the fake site just forwards what Rahul types to the real site, in real time.
  4. A hacked subdomain (blog.printkaro.com) passes the browser check, so the server's exact origin check is still needed.

This only protects Rahul if the account has no weaker way in. Keep a phishable "password + SMS" login around, and attackers phish that instead.
