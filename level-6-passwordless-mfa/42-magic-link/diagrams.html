How to read it

  1. Step 1 (top): the IP limit runs first. The email cooldown decides whether an email is sent, but the reply is the same 202 either way.
  2. Step 2: opening the link (a GET) only shows a confirm page. The token stays alive, so an email scanner that opens links can't burn it.
  3. Step 3: only the button (a POST) logs in. A foreign Origin is refused (login CSRF).
  4. The token is deleted before the expiry check, so it can never be used twice.
  5. Every bad token ends in the same red box: fake, used and expired look identical.

Clicking proves Rahul owns the inbox, so a brand-new user is created already verified. Sign-up and sign-in are the same flow.

2. Data flow

Rahul signs in to PrintKaro on his laptop with no password. Real requests, cookies and payloads.

sequenceDiagram
    autonumber
    actor U as Rahul
    participant B as Laptop browser
    participant S as PrintKaro server
    participant DB as Database
    participant M as Rahul's inbox

    U->>B: Types his email, presses "Email me a sign-in link"
    B->>S: POST /auth/magic-link { email: Rahul's, next: "/orders" }
    Note over S: IP limit OK, no email in the last minute<br/>token = randomBytes(32) → "j9Qe…pqlo"<br/>attempt = randomBytes(32) → "siwq…a08"
    S->>DB: DELETE old links for Rahul, INSERT { sha256("j9Qe…"), email, sha256("siwq…"), next: "/orders", expiresAt: +15 min }
    S->>M: "Your sign-in link" + printkaro.in/auth/verify?token=j9Qe…pqlo
    S-->>B: 202 "a link is on its way" + Set-Cookie: ml_attempt=siwq…a08 (HttpOnly, 15 min)
    M->>S: Mail scanner opens the link first: GET /auth/verify?token=j9Qe…
    S-->>M: 200 confirm page (token NOT used, scanner can't press buttons)
    U->>M: Opens the email, clicks the link in the laptop browser
    B->>S: GET /auth/verify?token=j9Qe… (cookie ml_attempt=siwq…)
    S->>DB: Find sha256("j9Qe…") (do NOT delete)
    Note over S: attempt hash matches → same browser, no warning
    S-->>B: 200 "Sign in to PrintKaro as Rahul?" [Sign in] (Referrer-Policy: strict-origin)
    U->>B: Presses "Sign in"
    B->>S: POST /auth/verify token=j9Qe… (Origin: printkaro.in)
    S->>DB: Find + DELETE sha256("j9Qe…"), not expired ✓
    S->>DB: Find Rahul, or INSERT { id: "u_1", emailVerified: true }
    S->>DB: INSERT session { sha256(sid), userId: "u_1", expiresAt: +7 days }
    S-->>B: 303 Location: /orders + Set-Cookie: sid=RbrS… (HttpOnly, SameSite=Lax), ml_attempt cleared
    B->>S: GET /orders (cookie sid=RbrS…)
    S-->>B: 200 Rahul's orders ✓

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Step 4: the database gets only hashes. The plain token goes only into the email (step 5); the plain attempt id only into Rahul's cookie (step 6).
  3. Steps 7–8: the mail scanner opens the link before Rahul does. Because GET only shows a page, nothing is used up.
  4. Step 12: the ml_attempt cookie proves this is the same browser that asked.
  5. Step 16: the token is found and deleted in one go. Step 19: a brand-new session id, and the next page came from the server, not from the link.

How to read it

  1. Left, login CSRF: if it worked, Rahul would be logged in as Vikram and might save his card or address into Vikram's account.
  2. The auto-submitted form is stopped by the Origin check on the POST.
  3. The link Rahul opens himself is stopped by a human: the confirm page shows whose account it is and that it was requested elsewhere.
  4. Right, link scanners: because scanners only GET, the rule "GET never logs in" keeps the single-use token for the real user.

Also blocked by the code: next: "//evil.com" becomes / (open redirect), the 11th request from one IP gets 429, and a second email to Rahul within a minute is silently skipped.
