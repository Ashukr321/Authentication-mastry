1. How a code is made

The phone and the server run the same steps on their own. No network needed: same secret + same time = same code.

The code on the screen The shared secret: set up once, kept safe 
flowchart TD
    S[("Shared secret<br/>20 random bytes<br/>base32: 63H4RT77…")] --> H
    T(["Current time<br/>1793864460 seconds since 1970"]) --> C["step = floor(time / 30)<br/>= 59795482"]
    C --> M["counter as 8 bytes<br/>00 00 00 00 03 90 68 1A"]
    M --> H["HMAC-SHA1(secret, counter)<br/>20 bytes"]
    H --> O["offset = last 4 bits<br/>of the last byte (0 to 15)"]
    O --> R["read 4 bytes at offset<br/>drop the top bit"]
    R --> D["number mod 1,000,000<br/>pad to 6 digits"]
    D --> OK[/"678117<br/>valid for this 30-second step"/]

    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class OK ok
    class S trap

How to read it

  1. Two inputs: the secret (yellow, shared once by QR code) and the clock.
  2. Time is cut into 30-second steps. Everyone in the same step gets the same counter.
  3. HMAC-SHA1 mixes the secret and the counter into 20 random-looking bytes.
  4. "Dynamic truncation": the last 4 bits pick where to read 4 bytes, which become a number.
  5. The last 6 digits are the code. The next step gives a completely different one.

This is HOTP (RFC 4226) with time as the counter, which is TOTP (RFC 6238). server.js checks its version against the RFC test vectors every time it starts.

2. Setup flow

Rahul is logged in and turns on 2FA: POST /2fa/setup, then POST /2fa/enable.

How to read it

  1. Setup makes the secret and stores it encrypted: the server must read it back later, so it can't be hashed.
  2. The QR code is just the otpauth:// URL. Make it on your side, never with an online QR website.
  3. 2FA is still off after setup. A wrong scan can't lock Rahul out.
  4. One correct code proves the app works. Only then is 2FA switched on.
  5. The recovery codes are shown once. The server keeps only their hashes.

3. Login data flow

Rahul logs in with his password, then the code from his phone. A ticket in between, a session only at the end.

sequenceDiagram
    autonumber
    actor U as Rahul
    participant B as Browser
    participant S as PrintKaro server
    participant DB as Database
    participant Ph as Authenticator app

    U->>B: Types email + password
    B->>S: POST /login { email, password }
    S->>DB: Find Rahul, scrypt check ✓, totp.enabled = true
    Note over S: mfaToken = randomBytes(32) → "lOBH…fwVo"
    S->>DB: INSERT ticket { sha256("lOBH…"), userId, expiresAt: +5 min, attempts: 0 }
    S-->>B: 200 { mfaRequired: true, mfaToken: "lOBH…" } (NO session cookie)
    U->>Ph: Opens the app
    Note over Ph: HOTP(secret, floor(now / 30)) → 663287<br/>(offline, no network)
    Ph-->>U: 663287
    U->>B: Types 663287
    B->>S: POST /login/2fa { mfaToken: "lOBH…", code: "663287" }
    S->>DB: Find ticket, attempts + 1, user fails this hour below 10 ✓
    S->>DB: Read + DECRYPT the TOTP secret
    Note over S: try steps now-1, now, now+1<br/>skip steps ≤ lastUsedStep (replay)<br/>timingSafeEqual → match at step "now" ✓
    S->>DB: lastUsedStep = now, DELETE ticket, reset fails
    S->>DB: INSERT session { sha256(sid), userId, expiresAt: +7 days }
    S-->>B: 200 "Logged in with 2FA" + Set-Cookie: sid=nQTv… (HttpOnly, SameSite=Lax)

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Step 6: a right password gives only a ticket (5 minutes, single use), never a session.
  3. Step 8: the phone computes the code offline. Nothing is sent to it, so there's nothing to intercept.
  4. Step 12: the attempt is counted first. Step 14: the ±1 window allows for clock drift, and old steps are refused.
  5. Step 15: lastUsedStep moves forward, so 663287 can never be used again, even within its 30 seconds.

Lost phone? In step 11 send recoveryCode instead of code. The server deletes that recovery code's hash, so it works once.
