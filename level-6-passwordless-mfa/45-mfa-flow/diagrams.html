1. Login flow

Everything that can happen from "type your password" to "you're in". Three requests: POST /login, (maybe) POST /login/mfa/email, POST /login/mfa.

Session created Error: no session In between: a ticket, not a session

    B -- No --> E1[/"401 Invalid email or password"/]

How to read it

  1. The password is always checked first. Codes are only sent after that, so nobody can spam Rahul's inbox with just his email.
  2. A valid trusted-device cookie skips the code, but the session gets mfaAt: null. That matters for step-up (section 3).
  3. The yellow ticket is not a session: it can't open any page, only be traded for one with a factor.
  4. Two limits: 5 tries per ticket, and 10 per user per hour across all tickets.
  5. Success records how (amr) and when (mfaAt), and can remember the device.

2. Data flow

Monday: Rahul logs in with a TOTP code and ticks "remember this device". Thursday: same laptop, no code needed.

sequenceDiagram
    autonumber
    actor U as Rahul
    participant B as Laptop browser
    participant S as PrintKaro server
    participant DB as Database
    participant Ph as Authenticator app

    Note over U,Ph: Monday
    B->>S: POST /login { email, password }
    S->>DB: scrypt check ✓, methods: totp, email_otp, recovery_code
    Note over S: no td cookie → MFA needed
    S->>DB: INSERT ticket { sha256(mfaToken), userId, +5 min, attempts: 0 }
    S-->>B: 200 { mfaRequired: true, mfaToken: "1816…", methods: [totp, email_otp, recovery_code] }
    U->>Ph: Opens the app
    Ph-->>U: 471168
    B->>S: POST /login/mfa { mfaToken, method: "totp", code: "471168", rememberDevice: true }
    S->>DB: attempts + 1, TOTP ✓ (step not used before), DELETE ticket
    S->>DB: INSERT session { amr: [pwd, totp], mfaAt: now }
    S->>DB: INSERT trusted device { sha256(td), userId, "Chrome on Windows", +30 days }
    S-->>B: 200 + Set-Cookie: sid=t0n2… (Path=/) + Set-Cookie: td=SXIf… (Path=/login, 30 days)
    Note over U,Ph: Thursday: logged out, logs in again
    B->>S: POST /login { email, password } + cookie td=SXIf…
    S->>DB: scrypt check ✓, find sha256("SXIf…")
    DB-->>S: { userId: Rahul ✓, expires in 26 days ✓ }
    S->>DB: INSERT session { amr: [pwd], mfaAt: null, viaTrustedDevice: true }
    S-->>B: 200 "Trusted device: 2FA skipped" + Set-Cookie: sid=…

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Step 5: the password gives only a ticket. No session cookie yet.
  3. Step 9: the ticket is deleted as soon as it's used, and the TOTP step is marked used (no replay).
  4. Step 12: two cookies. sid goes everywhere; td only to /login. Both are random and stored hashed.
  5. Steps 13–17: the device is found and belongs to Rahul, so the code is skipped. The password was still needed.

Rahul changes his password because he thinks it leaked? Delete all his trusted devices too, or the attacker's laptop stays trusted.

3. Step-up: logged in is not enough

Thursday's trusted-device session wants to change where PrintKaro sends Rahul's money: POST /account/payout.

Action allowed Blocked: confirm first The step-up 
flowchart TD
    A(["POST /account/payout<br/>{ upiId: rahul@okicici }"]) --> B{"Signed in?"}
    B -- No --> E0[/"401 Not signed in"/]
    B -- Yes --> C{"mfaAt set and<br/>less than 5 min ago?"}
    C -- Yes --> OK[/"200 Payout UPI ID saved<br/>+ email: your payout was changed"/]
    C -- "No: trusted-device login,<br/>or MFA was days ago" --> E1[/"403 Please confirm it's you<br/>stepUpRequired: true, methods"/]
    E1 --> F["Frontend shows the code box<br/>(email code: POST /step-up/email first)"]
    F --> G["POST /step-up<br/>{ method, code }"]
    G --> H{"Code right?<br/>(same limits as login)"}
    H -- No --> E2[/"401 Wrong code, attemptsLeft"/]
    H -- Yes --> U["session.mfaAt = now<br/>amr gets the method added"]
    U -. "retry" .-> A

How to read it

  1. The check is time-based: mfaAt must be recent, not just "this session once passed MFA".
  2. A trusted-device login has mfaAt: null, so it always has to step up first.
  3. The 403 says which methods work, so the frontend can show the right box.
  4. Step-up updates the same session. No new login, just a fresh mfaAt.
  5. The action itself also sends an alert email, so if it wasn't Rahul, he finds out right away.

Also protect this way: changing email, phone or password, turning 2FA off, recovery codes, API keys, deleting the account, forgetting trusted devices.
