1. Flow diagram: does the browser send this cookie?

Before every request, the browser (not the server) runs these checks for each cookie it has stored. The cookie is attached only if all of them pass.

Cookie is sent Cookie is not sent Expired: deleted by the browser 
flowchart TD
    A(["The browser is about to send a request<br/>e.g. GET shop.com/cart"]) --> B{"Does the Domain match?<br/>no Domain: exact host only<br/>Domain=shop.com: also subdomains"}
    B -- No --> N1[/"Not sent"/]
    B -- Yes --> C{"Does the Path match?<br/>Path=/admin: only /admin/..."}
    C -- No --> N1
    C -- Yes --> D{"Expired?<br/>Max-Age or Expires has passed"}
    D -- Yes --> DEL["The browser deletes it"]
    DEL --> N1
    D -- No --> E{"Secure cookie, but the<br/>request is plain http://?"}
    E -- Yes --> N1
    E -- No --> F{"Is the request<br/>same-site?"}
    F -- Yes --> OK[/"Sent<br/>Cookie: name=value"/]
    F -- "No, cross-site" --> G{"SameSite value?"}
    G -- None --> OK
    G -- Strict --> N2[/"Not sent<br/>(this is what blocks CSRF)"/]
    G -- Lax --> H{"Top-level GET navigation?<br/>e.g. clicking a link"}
    H -- Yes --> OK
    H -- "No: POST, iframe, fetch, img" --> N2

How to read it

  1. Start at the top: the browser is about to send a request.
  2. Diamonds are the browser's questions, one per flag. Follow Yes or No.
  3. Domain, Path, Max-Age and Secure come first. Failing any of them means "not sent".
  4. SameSite only matters for cross-site requests (started by another website).
  5. Lax allows clicking a link, but blocks a cross-site form POST, which is exactly what a CSRF attack uses.

HttpOnly isn't in this chart because it doesn't change sending. It only hides the cookie from JavaScript (see the data flow).

2. Data flow: the flags protecting a session

One session cookie with the recommended flags, facing an XSS script and a CSRF attack from evil.com, plus a normal link click that still works.

sequenceDiagram
    autonumber
    participant S as shop.com (server)
    participant B as Browser (cookie jar)
    participant X as XSS script on shop.com
    participant E as evil.com

    S-->>B: Set-Cookie: __Host-sessionId=k9X2… (HttpOnly, Secure, SameSite=Lax, Path=/)
    Note over B: Stores the value together with its rules
    B->>S: GET https://shop.com/cart + Cookie: __Host-sessionId=k9X2…
    Note over S: The server only receives name=value,<br/>never the flags
    X->>B: Reads document.cookie
    B-->>X: "" (HttpOnly cookies are hidden from JavaScript)
    Note over X: Can't steal the session ✓
    E->>B: A hidden form auto-submits POST https://shop.com/transfer
    Note over B: Cross-site POST + SameSite=Lax<br/>so the cookie is NOT attached
    B->>S: POST /transfer (no cookie)
    S-->>B: 401 Please log in (CSRF blocked ✓)
    E->>B: The user clicks a normal link to https://shop.com
    Note over B: Cross-site, but a top-level GET + Lax<br/>so the cookie IS attached
    B->>S: GET https://shop.com + Cookie: __Host-sessionId=k9X2…
    S-->>B: 200 OK, still logged in ✓
    Note over B,S: Over plain http://shop.com, this Secure cookie<br/>would never be sent at all

How to read it

  1. Each column is one actor. The browser is the one enforcing the rules.
  2. Solid arrows are requests or actions, dashed arrows are replies.
  3. Steps 4–5: HttpOnly hides the cookie from the XSS script.
  4. Steps 6–8: SameSite=Lax drops the cookie from evil.com's form POST.
  5. Steps 9–11: a normal link from another site still keeps you logged in.

The server can't see the flags. It only receives Cookie: name=value. All the protection comes from the browser following the rules the server set in Set-Cookie.

Diagrams are drawn with Mermaid, which loads from the internet the first time you open this page.
