1. Flow diagram

Every decision the server makes, from the moment the request arrives until it sends a response.

Success Error: the server stops here Timing-attack fix (dummy hash) Session store 
flowchart TD
    A([User submits the login form]) --> B["POST /login<br/>{ email, password }"]
    B --> C{"email and password are<br/>non-empty strings?"}
    C -- No --> E1[/"400 Bad Request<br/>Email and password are required"/]
    C -- Yes --> D["Normalize email<br/>trim + lowercase"]
    D --> F{"User found<br/>by email?"}
    F -- Yes --> G["Verify password against<br/>the user's stored hash"]
    F -- No --> G2["Verify password against a DUMMY hash<br/>(takes the same time, always fails)"]
    G --> M{"Password<br/>matches?"}
    M -- No --> E2[/"401 Unauthorized<br/>Invalid email or password"/]
    G2 --> E2
    M -- Yes --> N["Create a NEW random session ID<br/>crypto.randomBytes(32)"]
    N --> O[("Save session<br/>sessionId → userId")]
    O --> P[/"200 OK<br/>Set-Cookie: sessionId (HttpOnly)<br/>{ id, email }"/]

How to read it

  1. Start at the top: the user submits the form.
  2. Diamonds are questions the server asks. Follow Yes or No.
  3. Both "user not found" and "wrong password" end in the same red box, with the same message, so attackers learn nothing.
  4. The yellow box runs a dummy hash so "user not found" takes as long as "wrong password".
  5. Green box: logged in, and the browser gets a session cookie.

Without the yellow box, an attacker could tell which emails exist just by timing the response.

How to read it

  1. Each column is one part of the system.
  2. Solid arrows are requests, dashed arrows are replies.
  3. The numbers show the order things happen.
  4. Yellow notes are what the server does on its own.
  5. The alt box shows the two possible endings.
Diagrams are drawn with Mermaid, which loads from the internet the first time you open this page.
