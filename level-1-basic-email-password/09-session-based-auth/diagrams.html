1. Flow diagram

What the server checks on every request to a protected page. In real apps this check lives in one requireAuth middleware.

Success Error: the server stops here Expired: the session is deleted Session store 
flowchart TD
    A(["Request to a protected page<br/>e.g. GET /me"]) --> B{"Does the cookie<br/>have a sessionId?"}
    B -- No --> E1[/"401 Unauthorized<br/>Please log in"/]
    B -- Yes --> C["key = sha256(sessionId)"]
    C --> D[("Look up the key<br/>in the session store")]
    D --> F{"Session<br/>found?"}
    F -- No --> E1
    F -- Yes --> G{"Idle too long?<br/>no request for 30 min"}
    G -- Yes --> X["Delete the session<br/>from the store"]
    G -- No --> H{"Too old?<br/>created more than 8 h ago"}
    H -- Yes --> X
    X --> E2[/"401 Unauthorized<br/>Session expired, please log in again"/]
    H -- No --> I["Refresh: lastSeenAt = now<br/>(sliding idle timeout)"]
    I --> J["Load the user by session.userId"]
    J --> OK[/"200 OK<br/>the page for rahul"/]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class E1,E2 error
    class OK ok
    class X trap

How to read it

  1. Start at the top: a request arrives with (or without) a cookie.
  2. Diamonds are questions the server asks. Follow Yes or No.
  3. The server hashes the ID before looking it up, so a leaked store is useless.
  4. Two timers: idle (no activity) and absolute (too old). Either one ends the session.
  5. The yellow box: expired sessions are deleted right away.
  6. Every successful request refreshes lastSeenAt, so active users stay logged in.

The server checks expiry itself. It never trusts the cookie's Max-Age, because an attacker can keep using an old cookie value.

2. Data flow

The whole life of one session: created at login, read on every request, deleted at logout. It also shows why a stolen cookie stops working after logout.

sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant S as Server
    participant SS as Session store
    actor A as Attacker

    U->>B: Logs in with email + password
    B->>S: POST /login { email, password }
    Note over S: Password correct ✓<br/>sessionId = randomBytes(32) → "k9X2…"
    S->>SS: SET sha256("k9X2…") → { userId: "u_1", createdAt, lastSeenAt }
    S-->>B: 200 OK + Set-Cookie: sessionId=k9X2… (HttpOnly)
    Note over B: The cookie holds ONLY the random ID.<br/>No name, no email, no password.
    U->>B: Opens the profile page
    B->>S: GET /me + Cookie: sessionId=k9X2… (sent automatically)
    S->>SS: GET sha256("k9X2…")
    SS-->>S: { userId: "u_1", lastSeenAt: 10:30 }
    Note over S: Not expired ✓<br/>Refresh lastSeenAt = 10:42
    S-->>B: 200 OK { "email": "rahul@mail.com" }
    Note over A: Somehow copies the cookie "k9X2…"
    U->>B: Clicks "Log out"
    B->>S: POST /logout + Cookie: sessionId=k9X2…
    S->>SS: DELETE sha256("k9X2…")
    S-->>B: 204 + Set-Cookie: sessionId= (Max-Age=0)
    A->>S: GET /me + Cookie: sessionId=k9X2… (the stolen copy)
    S->>SS: GET sha256("k9X2…")
    SS-->>S: nothing found
    S-->>A: 401 Please log in
    Note over S,A: The stolen cookie is useless after logout,<br/>because the session no longer exists on the server

How to read it

  1. Each column is one part of the system. The Attacker is someone who copied the cookie.
  2. Solid arrows are requests, dashed arrows are replies.
  3. The numbers show the order things happen.
  4. The browser only ever holds k9X2…. The real data (userId, timestamps) stays in the session store.
  5. Steps 15–18: after logout, the stolen copy points to nothing.

3. Scaling: why the store must be shared

Real apps run several copies of the server behind a load balancer. Each request can land on a different server.

❌ In-memory store

Each server has its own memory

flowchart TB
    B1[Browser] --> LB1{{Load balancer}}
    LB1 -->|"step 1: POST /login"| SA["Server A<br/>memory: k9X2 → u_1"]
    LB1 -->|"step 2: GET /me"| SB["Server B<br/>memory: empty"]
    SB --> R1[/"401 Please log in 😕"/]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    class R1 error

✅ Shared store

All servers use one Redis

flowchart TB
    B2[Browser] --> LB2{{Load balancer}}
    LB2 -->|"step 1: POST /login"| SC[Server A]
    LB2 -->|"step 2: GET /me"| SD[Server B]
    SC -->|"save session"| RD[("Redis<br/>k9X2 → u_1")]
    SD -->|"look up session"| RD
    SD --> R2[/"200 OK ✓"/]

    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    class R2 ok

How to read it

  1. ❌ In-memory store: login lands on Server A and the session is saved in A's memory.
  2. The next request lands on Server B, which has never seen that session, so the user is "logged out".
  3. ✅ Shared store: both servers read and write one shared Redis, so any server can find any session.

Another option is sticky sessions (the load balancer always sends a user to the same server), but sessions are still lost when that server restarts. A shared store is the standard fix.
