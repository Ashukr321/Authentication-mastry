1. Flow diagram

What the frontend's api() wrapper does on every request

The user sees the data Login page / real error Shared refresh: one call for everyone waiting 
flowchart TD
    A(["api('/me')<br/>Authorization: Bearer token-in-memory"]) --> R{"Response?"}
    R -- "200" --> OK[/"Show the data"/]
    R -- "403 / 5xx /<br/>401 invalid_token" --> ERR[/"Real error:<br/>don't refresh"/]
    R -- "401 token_expired" --> P{"A refresh already<br/>in flight?"}
    P -- Yes --> W["Await the SAME<br/>refreshPromise"]
    P -- No --> N["Start POST /auth/refresh,<br/>save it as refreshPromise"]
    N --> W
    W --> RF{"Refresh OK?"}
    RF -- No --> LOGIN[/"Clear token + timer,<br/>show the login page"/]
    RF -- Yes --> RT["Retry the request ONCE<br/>with the new token"]
    RT --> OK

How to read it

  1. Every API call goes through one wrapper (or an axios interceptor).
  2. Only 401 token_expired triggers a refresh. A tampered token or a 403 won't be fixed by refreshing.
  3. The yellow boxes are single-flight: 5 expired requests share 1 refresh call.
  4. The request is retried once. There is no arrow back to the top, so no endless loop.
  5. If the refresh fails, the refresh token is dead: go to the login page.

2. Data flow

Rahul's dashboard: the timer refreshes early once. Later the laptop sleeps, the token expires, and 5 requests fire at the same moment.

sequenceDiagram
    autonumber
    participant B as Rahul's browser
    participant S as Server

    B->>S: POST /auth/login { email, password }
    S-->>B: 200 { accessToken: "eyJ…A", expiresIn: 900 } + refreshToken cookie
    Note over B: timer set for 900 - 60 = 840 s
    Note over B,S: 14 minutes later: timer fires (proactive)
    B->>S: POST /auth/refresh (cookie)
    S-->>B: 200 { accessToken: "eyJ…B", expiresIn: 900 }
    Note over B: the laptop sleeps, the timer is missed, "eyJ…B" expires
    par 5 requests at the same moment
        B->>S: GET /me, /orders, /cart, … (Bearer eyJ…B)
    end
    S-->>B: 401 token_expired (×5)
    Note over B: first 401 starts the refresh, the other 4 await the same promise
    B->>S: POST /auth/refresh (cookie), only ONE
    S-->>B: 200 { accessToken: "eyJ…C", expiresIn: 900 }
    B->>S: retry all 5 (Bearer eyJ…C)
    S-->>B: 200 (×5), Rahul saw nothing

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2: the server sends expiresIn, and the client sets a timer that fires early.
  3. Steps 3–4: proactive refresh. No request ever saw a 401.
  4. Steps 5–6: timers can be missed (sleep, throttled tabs), so expired requests still happen.
  5. Steps 7–10: the reactive safety net. One refresh, then every request is retried once.

3. Page load and the timer

The access token lives only in memory. The refresh cookie brings it back after a reload, and the timer keeps it fresh.
