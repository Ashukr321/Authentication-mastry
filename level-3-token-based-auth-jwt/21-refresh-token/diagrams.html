How to read it

  1. The refresh token arrives in an HttpOnly cookie that is sent only to /auth/*.
  2. Only the hash is in the database, so the lookup uses sha256(token).
  3. The yellow checks are why refresh tokens exist: logout, expiry, a banned or deleted user all stop here.
  4. The password is not needed. The old access token is not needed either.
  5. In this topic the refresh token is reused until it expires. Topic 23 replaces it on every refresh.

2. Data flow

Rahul logs in, uses the API, his access token expires, the app refreshes it, and then he logs out.

sequenceDiagram
    autonumber
    participant B as Rahul's browser
    participant S as Server
    participant DB as Database

    B->>S: POST /auth/login { email, password }
    S->>DB: check password (scrypt)
    S->>DB: INSERT refresh sha256("e5bf…") → { u_1, +7 days }
    S-->>B: 200 { accessToken: "eyJ…", expiresIn: 900 } + refreshToken=e5bf… (HttpOnly, Path=/auth)
    B->>S: GET /me (Authorization: Bearer eyJ…)
    Note right of S: verify signature + exp only, no DB
    S-->>B: 200 { email of u_1 }
    Note over B,S: 15 minutes later
    B->>S: GET /me (Bearer eyJ… expired)
    S-->>B: 401 { code: "token_expired" }
    B->>S: POST /auth/refresh (cookie refreshToken=e5bf…)
    S->>DB: find sha256("e5bf…"): not expired, user u_1 exists ✓
    S-->>B: 200 { accessToken: "eyJ…new" }
    B->>S: GET /me (Bearer eyJ…new), retried
    S-->>B: 200 { email of u_1 }
    B->>S: POST /auth/logout (cookie refreshToken=e5bf…)
    S->>DB: DELETE refresh sha256("e5bf…")
    S-->>B: 200 + refreshToken cleared
    Note over B,S: "eyJ…new" still works until its exp, then refresh fails: 401, log in again

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–4: the password is checked once. Login returns a pair; only the refresh token's hash is stored.
  3. Steps 5–6: normal API calls never touch the database.
  4. Steps 7–8: the access token expired, so the API answers token_expired.
  5. Steps 9–13: the browser trades the refresh token for a new access token and retries. The user sees nothing.
  6. Steps 14–16: logout deletes the refresh token on the server. The last access token dies on its own.

3. Access vs refresh: two tokens, two jobs

The token sent everywhere is short-lived. The long-lived token goes to one endpoint only.

Used on every API call Used only to get a new access token
