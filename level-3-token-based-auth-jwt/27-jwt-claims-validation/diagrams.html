1. Flow diagram

The checks in order. Each red exit is the attack that check stops.

Trusted 401 Invalid access token Checks you must add yourself (not library defaults) 
flowchart TD
    A(["Authorization: Bearer header.payload.signature"]) --> ALG{"header.alg in<br/>the allow-list (RS256)?"}
    ALG -- "No: none, HS256 with<br/>the public key" --> X[/"401<br/>+ log the real reason"/]
    ALG -- Yes --> SIG{"Signature valid<br/>with OUR public key?"}
    SIG -- "No: tampered payload" --> X
    SIG -- Yes --> ISS{"iss = auth.example.com?"}
    ISS -- "No: staging, other tenant" --> X
    ISS -- Yes --> AUD{"aud includes orders-api?"}
    AUD -- "No: made for another API" --> X
    AUD -- Yes --> T{"exp, nbf OK<br/>(± 30 s tolerance)?<br/>iat not too old?"}
    T -- "No: expired, not yet valid" --> X
    T -- Yes --> F{"iat not in the future?"}
    F -- No --> X
    F -- Yes --> TYP{"header.typ = at+jwt?"}
    TYP -- "No: refresh or ID token" --> X
    TYP -- Yes --> SUB{"sub present?"}
    SUB -- No --> X
    SUB -- Yes --> OK[/"✅ trust the payload,<br/>look up the user by sub"/]

How to read it

  1. The first five checks are done by jwt.verify, but only if you pass algorithms, issuer, audience, clockTolerance and maxAge.
  2. The yellow checks aren't in the library: you write them.
  3. Every failure goes to the same red box: one generic 401, the detail only in the log.
  4. Put all of this in one middleware, so no route forgets a check.

2. Data flow

Rahul's real token, then three attack tokens, against the orders API.

sequenceDiagram
    autonumber
    participant R as Rahul's app
    actor A as Attacker
    participant API as orders-api
    participant LOG as Server log

    R->>API: GET /orders (RS256, iss auth, aud orders-api, typ at+jwt, sub u_rahul)
    API-->>R: 200 orders of u_rahul
    A->>API: GET /orders (alg none, sub u_admin, no signature)
    API->>LOG: rejected: jwt signature is required
    API-->>A: 401 Invalid access token
    A->>API: GET /orders (HS256 signed with our public key, sub u_admin)
    API->>LOG: rejected: invalid algorithm
    API-->>A: 401 Invalid access token
    A->>API: GET /orders (real RS256 token, but aud reports-api)
    API->>LOG: rejected: jwt audience invalid
    API-->>A: 401 Invalid access token
    Note over A,API: the attacker always sees the same message, and learns nothing about which check failed

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2: a token that passes every check.
  3. Steps 3–5: alg: none has no signature. Pinning algorithms rejects it.
  4. Steps 6–8: algorithm confusion. The public key is public, so anyone can make this token. Pinning RS256 rejects it.
  5. Steps 9–11: a genuine token, correctly signed, but made for another API. Only the aud check stops it.

3. What gets checked

The header and the payload both carry things you must check. The signature only proves nobody changed them.

jwt.verify does it (when you pass the option) You check it yourself

    H --> H2[/"typ: at+jwt<br/>your own check"/]
    H --> H3["kid: which key,<br/>from YOUR issuer's JWKS only"]

jwt.decode checks nothing. On the server, always jwt.verify with every option, plus your own checks, in one shared middleware.
