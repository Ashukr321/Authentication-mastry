How to read it

  1. Reading the header is only used to find the key by its kid.
  2. The yellow box: the key decides the algorithm. The attacker wrote the header, so its alg can't be trusted.
  3. The signature covers the exact text header.payload: one changed character and it fails.
  4. Only then are the claims checked (exp, iss, aud, more in topic 27).
  5. Every failure gives the client the same 401 Invalid token.

2. Data flow

The server makes an HS256 token for Rahul. Then Priya tries to edit it, and tries an unsigned one.

sequenceDiagram
    autonumber
    actor R as Rahul
    actor P as Priya (attacker)
    participant S as Server (secret hs-1)

    R->>S: POST /tokens { alg: "HS256" }
    Note over S: header = {"alg":"HS256","kid":"hs-1"}
    Note over S: payload = {"sub":"u_1","role":"user","exp":…}
    Note over S: signature = HMAC-SHA256("eyJhbGci….eyJuYW1l…", secret)
    S-->>R: 201 eyJhbGci….eyJuYW1l….bYXog8QL…
    R->>S: POST /verify (the same token)
    S-->>R: 200 { valid: true, payload: { sub: "u_1", role: "user" } }
    Note over P: Priya decodes the payload: no key needed
    P->>S: POST /verify (header . payload with role admin . OLD signature)
    S->>S: HMAC of the new text ≠ bYXog8QL…
    S-->>P: 401 invalid signature
    P->>S: POST /verify ({"alg":"none","kid":"hs-1"} . payload . empty)
    S->>S: key hs-1 allows only HS256
    S-->>P: 401 jwt signature is required

How to read it

  1. Each column is one actor. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2: the signature is an HMAC over header.payload with the server's secret.
  3. Steps 3–4: verifying the untouched token works, with no database lookup.
  4. Steps 5–7: Priya can read the payload, but changing it breaks the signature.
  5. Steps 8–10: an unsigned alg: none token fails because the key's algorithm is pinned.

3. HS256 vs RS256/ES256: who can sign, who can verify

With HS256, every verifier could also make tokens. With RS256/ES256, verifiers only get the public key.

Can only verify Can verify AND make tokens Never leaves the auth server 
flowchart TD
    K1(["HS256<br/>one shared secret"]) --> A1["Auth server<br/>signs with the secret"]
    K1 --> B1["Orders service<br/>verifies with the SAME secret"]
    K1 --> C1["Payments service<br/>verifies with the SAME secret"]
    B1 --> X1[/"Orders is hacked →<br/>attacker can MAKE<br/>admin tokens"/]
