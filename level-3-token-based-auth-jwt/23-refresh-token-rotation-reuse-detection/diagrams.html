1. Flow diagram

What POST /auth/refresh does with the token it receives

Rotated: new tokens 401: log in again Used token came back: theft alarm Refresh token store 
flowchart TD
    A(["POST /auth/refresh<br/>Cookie: refreshToken=RT"]) --> D[("Find row by sha256(RT)")]
    D --> F{"Found, not expired,<br/>user exists?"}
    F -- No --> NO[/"401 invalid or expired<br/>clear cookie"/]
    F -- Yes --> U{"usedAt set?<br/>(already exchanged once)"}
    U -- "Yes: REUSE" --> T["🚨 Revoke the WHOLE family<br/>email the user"]
    T --> T2[/"401 token_reused"/]
    U -- No --> M["Mark RT used<br/>(atomic: only if usedAt is still empty)"]
    M --> N["Issue RT-next:<br/>same family, same end date"]
    N --> OK[/"200 new access token<br/>+ Set-Cookie RT-next"/]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class NO,T2 error
    class OK ok
    class U,T trap

How to read it

  1. Used tokens are kept (with usedAt), not deleted, so a replay is recognized.
  2. The yellow path: a used token means two parties had it. Kill the whole family, because the server can't tell who is who.
  3. The green path: every refresh gives a new refresh token. Each one works once.
  4. "Mark used" must be atomic, or two parallel requests could both rotate the same token.
  5. The new token keeps the family's original end date, so rotation never extends the login.

2. Data flow

Priya copies Rahul's laptop token. The laptop keeps rotating, then Priya replays her old copy. Rahul's phone is a separate family.

sequenceDiagram
    autonumber
    participant L as Rahul's laptop
    actor P as Priya (copied RT1)
    participant S as Server
    participant DB as Database

    L->>S: POST /auth/login { email, password }
    S->>DB: INSERT RT1 { family F1, ends 12 Nov, usedAt: null }
    S-->>L: 200 + refreshToken=RT1
    Note over P: Priya copies RT1
    L->>S: POST /auth/refresh (RT1)
    S->>DB: RT1.usedAt = now, INSERT RT2 { F1, ends 12 Nov }
    S-->>L: 200 + refreshToken=RT2
    P->>S: POST /auth/refresh (RT1)
    S->>DB: RT1 already used 🚨
    S->>DB: DELETE every token of family F1 (RT1, RT2)
    S-->>P: 401 token_reused
    Note right of S: email Rahul about a possibly stolen login
    L->>S: POST /auth/refresh (RT2)
    S-->>L: 401 log in again
    Note over L,DB: Rahul's phone has family F2: not touched, still logged in

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–3: login starts family F1 with an end date that never moves.
  3. Steps 4–6: the laptop refreshes. RT1 is marked used, RT2 replaces it.
  4. Steps 7–10: Priya's copy is RT1, already used → the alarm. All of F1 is deleted.
  5. Steps 11–12: the laptop is logged out too. If Priya had refreshed first, the laptop's RT1 would have raised the same alarm, and Priya's RT2 would die.
