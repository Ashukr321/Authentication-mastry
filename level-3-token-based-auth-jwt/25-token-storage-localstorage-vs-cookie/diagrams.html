How to read it

  1. Mobile apps don't use cookies: the OS's secure storage is the answer.
  2. In a browser, the refresh token always goes in an HttpOnly cookie. It's the long-lived prize.
  3. The yellow boxes are cookies: the browser sends them automatically, so CSRF defenses are required.
  4. The access token can stay in memory (no CSRF) or also go in a cookie (simpler).
  5. localStorage is never the answer for tokens.

2. Data flow

The same injected script runs on Rahul's page three times, once for each storage. What does it carry back to the attacker's server?

sequenceDiagram
    autonumber
    participant X as XSS script (on the page)
    participant API as Our server
    participant E as Attacker's server

    Note over X: localStorage mode
    X->>X: read localStorage: accessToken + refreshToken
    X->>E: POST /collect { accessToken, refreshToken }
    Note right of E: 😱 refresh token works for 7 days from anywhere
    Note over X: memory mode (refresh in HttpOnly cookie)
    X->>X: localStorage empty, document.cookie empty
    X->>API: POST /auth/refresh (browser adds the HttpOnly cookie)
    API-->>X: 200 { accessToken }
    X->>E: POST /collect { accessToken }
    Note right of E: ⚠️ works for 15 minutes, no refresh token
    Note over X: cookie mode (both tokens HttpOnly)
    X->>API: POST /auth/refresh
    API-->>X: 200 { storage: cookie } (new cookies, no token in the body)
    X->>API: GET /me (cookie sent automatically)
    API-->>X: 200, acting as Rahul while the tab is open
    X->>E: POST /collect { nothing usable }

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2: localStorage hands over everything, including the 7-day refresh token.
  3. Steps 3–6: HttpOnly hides the refresh token, but the script can ask for a new access token and take that.
  4. Steps 7–11: with no token ever in JavaScript, nothing usable leaves. The script still acts as Rahul while the page is open.
  5. Storage limits the damage. Only preventing XSS stops it (Level 7).

3. XSS vs CSRF: which storage fears which attack

Moving tokens out of JavaScript's reach makes them automatic, and automatic means CSRF.

CSRF is easy to block (SameSite + Origin check). XSS theft from localStorage is not. That's why the refresh token belongs in an HttpOnly cookie.
