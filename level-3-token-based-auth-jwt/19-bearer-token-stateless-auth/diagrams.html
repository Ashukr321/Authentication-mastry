How to read it

  1. No header at all is 401 with a WWW-Authenticate hint. A broken header is the client's bug: 400.
  2. The server decides the algorithm. Trusting the token's own alg is how the alg: none attack works.
  3. The signature check catches any edit to the payload, like changing the email or the role.
  4. exp, iss and aud stop old tokens and tokens made for another app.
  5. Every box is maths in memory. The yellow box is the price: the server can't know the token was "logged out".

2. Data flow

Rahul logs in once, calls the API, an attacker forges a token, Rahul "logs out", and the server restarts.

sequenceDiagram
    autonumber
    participant R as Rahul's app
    participant A as Attacker
    participant S as API server
    participant DB as Users table

    R->>S: POST /login { email, password: "rahul password 123" }
    S->>DB: find Rahul, verify the scrypt hash ✓
    S->>S: jwt.sign({ sub: u_1, email, exp: +15 min, iss, aud }, JWT_SECRET)
    S-->>R: 200 { access_token: "eyJhbGc...", token_type: "Bearer", expires_in: 900 }
    Note over S,DB: Nothing saved. No session row, no Redis.
    R->>S: GET /me (Authorization: Bearer eyJhbGc...)
    S->>S: jwt.verify: signature ✓ exp ✓ iss ✓ aud ✓
    S-->>R: 200 { id: u_1, email: Rahul's, expiresAt }
    A->>S: GET /me (Bearer token with email changed to Priya's)
    S->>S: recompute signature: does not match ✗
    S-->>A: 401 WWW-Authenticate: Bearer error="invalid_token"
    R->>S: POST /logout (Authorization: Bearer eyJhbGc...)
    S-->>R: 200 "Delete the token on your side"
    R->>R: accessToken = null
    Note over R,S: A copy of eyJhbGc... (a leaked log, XSS) still works until exp
    Note over S,DB: Server restarts. Same JWT_SECRET, users table is empty.
    A->>S: GET /me (the old copied token)
    S->>S: jwt.verify: signature ✓ exp ✓
    S-->>A: 200 { id: u_1 } even though u_1 no longer exists

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies, arrows to itself are work done in memory.
  2. Steps 1–4: the password is checked once, and the server signs a token instead of saving a session.
  3. Steps 5–7: every later request only needs the token and the key. The users table isn't touched.
  4. Steps 8–10: editing the payload breaks the signature, so forging fails.
  5. Steps 11–13: "logout" only happens on the client. The server has nothing to delete.
  6. Steps 14–16: a copied token survives logout, a restart, even a deleted user, until exp. That's why access tokens are short (topic 20) and refresh tokens exist (topic 21).

How to read it

  1. Left (topic 09): the cookie is just a ticket number. Every request, every server must ask the shared store who it belongs to.
  2. Right (this topic): the token already says who you are. Each server checks the signature by itself, with no call to anyone.
  3. The dotted lines are not requests: the key is given to each server once, when it starts.
  4. With RS256 / ES256 (topic 18) the servers get only the public key, so they can verify tokens but never create them.

The left side can log someone out instantly (delete the row). The right side can't, so real apps combine them: a short stateless access token plus a stored refresh token (topics 20–24).
