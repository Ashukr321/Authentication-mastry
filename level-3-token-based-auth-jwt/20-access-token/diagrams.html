1. Flow diagram

Every check the API does on a request that carries an access token

Allowed Rejected Normal: refresh and retry 
flowchart TD
    A(["GET /admin/stats<br/>Authorization: Bearer eyJ..."]) --> H{"Header is<br/>Bearer + token?"}
    H -- No --> E1[/"401 Missing access token"/]
    H -- Yes --> S{"Signature valid with<br/>our secret, alg = HS256?"}
    S -- "No: edited, forged, alg none" --> E2[/"401 invalid_token"/]
    S -- Yes --> X{"exp still in the future?<br/>(5 s clock tolerance)"}
    X -- No --> E3[/"401 token expired<br/>client uses refresh token"/]
    X -- Yes --> I{"iss = auth.example.com<br/>aud = api.example.com?"}
    I -- No --> E4[/"401 invalid_token"/]
    I -- Yes --> R{"role in the token<br/>= admin?"}
    R -- No --> E5[/"403 Requires role: admin"/]
    R -- Yes --> OK[/"200 OK<br/>no database lookup needed"/]

How to read it

  1. The token must come in the Authorization header, never the URL.
  2. The signature check catches every edited or forged token. The algorithm is pinned, so the token can't choose it.
  3. An expired token is normal (yellow): the client gets a new one with its refresh token.
  4. Everything up to here is authentication (who are you?) and fails with 401.
  5. The role check is authorization (may you?) and fails with 403.

2. Data flow

Rahul logs in, uses his token, hits an admin route, then his token expires

sequenceDiagram
    autonumber
    participant C as Rahul's app
    participant A as API server
    participant DB as Database

    C->>A: POST /login { email, password: "rahul password 123" }
    A->>DB: find user, verify scrypt hash ✓
    A->>A: jwt.sign({ sub: "7acb…", role: "user", iss, aud, exp: now + 15 min }, secret)
    A-->>C: 200 { access_token: "eyJhbGci…", token_type: "Bearer", expires_in: 900 }
    C->>A: GET /me (Authorization: Bearer eyJhbGci…)
    A->>A: jwt.verify(token, secret, { algorithms: [HS256], iss, aud }) ✓
    A->>DB: load user 7acb… (only because /me shows profile data)
    A-->>C: 200 { id: "7acb…", role: "user", tokenExpiresAt }
    C->>A: GET /admin/stats (Authorization: Bearer eyJhbGci…)
    A->>A: verify ✓, but role = "user"
    A-->>C: 403 { error: "Requires role: admin" }
    Note over C,DB: 15 minutes pass
    C->>A: GET /me (same token)
    A->>A: verify: exp is in the past ✗
    A-->>C: 401 WWW-Authenticate: Bearer error="invalid_token" (expired)
    Note over C,A: The app now calls /refresh with its refresh token (topics 21-22)

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–4: the password is checked once, then the server signs a token and sends it back.
  3. Steps 5–8: the token is verified on the API itself, no session table.
  4. Steps 9–11: a valid token with the wrong role gets 403, not 401.
  5. Steps 12–14: after exp, the same token gets 401 with a reason in the header.

A session costs a database lookup on every request but can be killed at once. An access token costs nothing to check but can't be killed, which is why it lives only 5–15 minutes and a refresh token (topic 21) keeps the user logged in.
