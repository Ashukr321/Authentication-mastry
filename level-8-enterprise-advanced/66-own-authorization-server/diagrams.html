How to read it

  1. The first two checks fail on our own page. Until redirect_uri matches a registered value exactly, redirecting anywhere would be an open redirect.
  2. After that, errors go back to the app as ?error=…&state=…, so the app can show them.
  3. The login form is on the authorization server's page. That's the whole point of OAuth: the app never touches the password.
  4. /token checks the code against everything stored with it. PKCE means a stolen code can't be used without the verifier.
  5. The API trusts the token only after checking it with the AS's public key from JWKS.

The yellow boxes hold values that came from the browser. The POST to /authorize checks them all again, because hidden form fields can be edited.

2. Data flow

Rahul logs in to the ChaiCart web app through ChaiCart ID, with the real requests from the demo (ports 3166 and 3167).

sequenceDiagram

    actor R as Rahul's browser
    participant W as ChaiCart Web (chaicart-spa)

    Note over W: verifier = 32 random bytes / challenge = SHA256(verifier)

    AS-->>R: 200 login + consent page (hidden fields carry the request)
    R->>AS: POST /authorize (email, password, decision=allow + hidden fields)
    Note over AS: store sha256(code) with client, redirect_uri, challenge, nonce (60 s)
    AS-->>R: 302 localhost:5173/callback?code=Q3x...&state=xyz&iss=localhost:3166
    R->>W: GET /callback?code=...&state=xyz
    Note over W: state matches what it saved?
    W->>AS: POST /token grant_type=authorization_code, code, code_verifier, client_id
    Note over AS: unused? same client + redirect_uri? SHA256(verifier) = challenge?
    AS-->>W: access_token (at+jwt) + id_token (nonce n-42) + refresh_token
    W->>API: GET /orders (Bearer access_token)
    API->>AS: GET /.well-known/openid-configuration, then GET /jwks.json (once, cached)
    AS-->>API: keys: RSA public key, kid chaicart-2026-11
    Note over API: verify RS256, iss, aud chaicart-api, exp, typ, scope orders:read
    API-->>W: 200 Rahul's 2 orders

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–3: the app only builds a URL. The browser goes to the AS, and the AS shows its own login page.
  3. Step 6: the code travels through the browser, so it's treated as exposed. That's why it's short-lived, single-use and bound to PKCE.
  4. Step 8: the code is swapped for tokens directly between the app and the AS (a back-channel call).
  5. Steps 10–12: the API needs no shared secret with the AS. It downloads the public key once and checks every token itself.

The ID token is for the app (aud = chaicart-spa). Send it to the API and it gets 401: wrong typ, wrong aud.

How to read it

  1. Every refresh gives a new refresh token and marks the old one used (topic 23).
  2. A used token coming back means two people have it. The AS can't tell who's the thief, so it kills the whole chain.
  3. A machine client proves itself with its secret. There's no user to log in, so there's nothing to refresh: it just asks again.

Already-issued access tokens (JWTs) still work until they expire, even after revocation. Keep them short, or use introspection (topic 70).
