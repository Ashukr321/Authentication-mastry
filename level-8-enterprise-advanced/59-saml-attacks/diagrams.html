How to read it

  1. The SAMLResponse (yellow) went through the attacker's browser. Every byte is attacker input, including DOCTYPE and KeyInfo.
  2. Top to bottom is the order of the safe checks: parse safely, verify, then read only from what was verified.
  3. Each red box is one bug in /vulnerable/acs. Each green box is the matching fix in /acs.
  4. Even with a perfect signature check, the bottom diamond still matters: a real IdP signature on someone else's or an old assertion is still a valid signature.

Comment injection passes the signature check on the safe side too. It's stopped by reading the full NameID, which then has no HR account (403).

2. Data flow

XML Signature Wrapping, with the real flow from the demo. Vikram starts with his own honest login, and the same forged response goes to both ACS endpoints.

sequenceDiagram
    autonumber
    actor V as Vikram (partner account)
    participant S as ChaiCart HR (SP, localhost:3159)
    participant I as ChaiCart IdP (localhost:3160)
    participant E as Vikram's toolkit (127.0.0.1:3161)

    V->>S: GET /login
    S-->>V: 302 to IdP /sso?SAMLRequest (ID _74cd, saved as pending)
    V->>I: POST /sso (his own email and password)
    Note over I: Assertion ID _2de7, NameID priya@chaicart.in.evil.dev, signed with the IdP key
    I-->>V: SAMLResponse (InResponseTo _74cd, Audience chaicart-hr)
    V->>E: POST /forge/xsw (his SAMLResponse)
    Note over E: copy the Assertion, remove its Signature, new ID _1793, NameID priya@chaicart.in
    Note over E: insert the copy BEFORE the real one. Reference URI still says #_2de7
    E-->>V: forged SAMLResponse (2 Assertions)
    V->>S: POST /vulnerable/acs
    Note over S: signature points at _2de7: valid. Reads Assertion [0] = _1793
    S-->>V: 200 Welcome priya@chaicart.in, role admin, salaries 😱
    V->>S: POST /acs (same forged response)
    Note over S: findAll Assertion at any depth = 2
    S-->>V: 401 expected exactly 1 Assertion, found 2 ✓

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–5: a completely normal SP-initiated login. The IdP did nothing wrong.
  3. Step 6 and the notes: the toolkit never touches the signed bytes. It only adds an unsigned assertion.
  4. Steps 10–12: the vulnerable ACS asks "is the signature valid?" (yes, for _2de7) and then "who is this?" (from _1793). Two different answers to "which assertion?".
  5. Steps 13–15: the safe ACS counts assertions first, so there's only one possible answer.

Swap xsw for strip, selfsigned or comment in step 6 and the shape is the same: vulnerable says 200 as Priya, safe says 401 or 403.

3. What the signature checks vs what the app reads

How to read it

  1. Green is what the IdP's signature really protects. Both attacks leave it untouched, so the signature stays valid.
  2. Left: the signature protects _2de7, but [0] is _1793. Fix: exactly one Assertion, read from the verified element.
  3. Right: canonicalization joins the two text nodes and ignores the comment. Code that takes only the first text node gets a different string. Fix: read all text nodes.

The general rule for both: the value you use must come from exactly the bytes you verified, read the same way the verifier read them.
