How to read it

  1. The app first checks its own session. Only without one does SSO start.
  2. The IdP only works for registered apps and only sends to their fixed ACS URL.
  3. The yellow box is the whole point of SSO: with an IdP session, no password is asked.
  4. The app checks the signature first, then every field. Each red box is an attack from the demo.
  5. Users are matched by the IdP's stable sub, never by email alone.

Every red box was hit in the README's curl run (steps ⑥ to ⑩).

    R->>P: GET /
    P-->>R: 302 to IdP /sso?sp=payroll and a new request_id
    R->>I: GET /sso?sp=payroll (cookie idp_sid)
    Note over I: IdP session found: NO password
    I-->>R: auto-submit form to Payroll's ACS { assertion: aud payroll }
    R->>P: POST /acs { assertion }
    P-->>R: 303 to / (cookie payroll_sid) ✓ single sign-on

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. The apps and the IdP never talk directly during login: the browser carries every message (redirects and an auto-submitting form).
  3. Steps 1–2: HR remembers the request_id in a cookie, so the answer must belong to this browser.
  4. Steps 5–7: the password is typed only at the IdP. HR never sees it.
  5. Steps 8–10: HR checks the assertion, then creates its own session.
  6. Steps 11–17: Payroll goes through the same dance, but the IdP already has a session: no login page.

How to read it

  1. Left: logging out of one app only ends that app's session. Because the IdP session is alive, the next visit is an instant SSO login. Users often think "logout is broken".
  2. Right: logging out of the IdP stops new logins, but apps that already have their own session keep working until it expires.
  3. The same is true when an admin disables a user at the IdP: keep app sessions short, and use Single Logout (topic 61) or SCIM (topic 62) to end them.
