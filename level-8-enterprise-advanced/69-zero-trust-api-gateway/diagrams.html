How to read it

  1. There are two ways in: through the gateway, or straight to the service from inside the network. Zero trust has to hold for both.
  2. The gateway first drops identity headers the client sent. Only the gateway says who the user is.
  3. It authenticates the opaque token by looking it up, so logout is instant.
  4. It checks role and device. The device check (yellow) is live: the MDM can flip it at any time.
  5. It mints a token for one service, valid 60 seconds, signed with a key services can't use to sign.
  6. The service verifies everything again and checks the role itself. That's "assume breach".

The dotted arrow is the one-line bug from the demo: the client's headers spread after the gateway's own.

2. Data flow: perimeter vs zero trust

Rahul (employee, not HR) tries to read payroll. The perimeter model on top, zero trust below, with the real responses from the README run.

    participant P as payroll-service :3070

    R->>G: POST /login (Rahul, rahul-laptop)
    G-->>R: 200 access_token dhLuUD… (opaque)

    Note over R,L: ❌ Perimeter model
    R->>G: GET /vulnerable/api/payroll + X-User priya
    Note over G: token OK, headers = x-user Rahul, then ...client x-* headers
    G->>L: X-User priya (Rahul's own value overwritten)
    L-->>R: 200 every salary 😱
    R->>L: GET /legacy/payroll + X-User priya (no gateway, no token)
    L-->>R: 200 every salary 😱

    Note over R,P: ✅ Zero trust
    R->>G: GET /api/payroll + X-User priya
    Note over G: drop x-user, Rahul's roles = employee, route needs hr
    G-->>R: 403 This API needs the "hr" role
    R->>P: GET /payroll + X-User priya (no gateway)
    P-->>R: 401 payroll-service: no token

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2: Rahul gets an opaque token. It says nothing on its own; only the gateway can look it up.
  3. Steps 3–5: the perimeter gateway lets his X-User win, and the legacy service believes it.
  4. Steps 6–7: from inside the network he doesn't even need the gateway. This is what "trust the network" costs.
  5. Steps 8–9: the zero trust gateway ignores the header and judges Rahul by his own token.
  6. Steps 10–11: the real payroll service wants a signed token, so the inside door is shut too.

3. Data flow: assume breach

What if an attacker hacks orders-service and steals the tokens it receives? And what if a laptop goes unhealthy mid-session?

sequenceDiagram
    autonumber
    actor A as Attacker (inside orders-service)
    actor Pr as Priya (HR)
    participant G as API gateway :3069
    participant O as orders-service
    participant P as payroll-service
    participant M as MDM

    G->>O: Bearer JWT (sub Rahul, aud orders-service, exp 60 s)
    Note over A,O: attacker copies that JWT
    A->>P: GET /payroll, Bearer stolen JWT
    P-->>A: 401 wrong audience (made for orders-service)
    A->>P: same JWT, payload edited to aud payroll-service + role hr
    P-->>A: 401 bad signature (no private key to re-sign)

    Pr->>G: GET /api/payroll (from priya-mbp)
    G->>P: Bearer JWT (aud payroll-service)
    P-->>Pr: 200 payroll
    M->>G: priya-mbp compliant false (disk encryption turned off)
    Pr->>G: GET /api/payroll (same valid token)
    G-->>Pr: 403 healthy company device needed
    M->>G: priya-mbp compliant true
    Pr->>G: GET /api/payroll
    G-->>Pr: 200 payroll again, no new login

    Note over A,O: 60 s later
    A->>O: GET /orders, Bearer stolen JWT
    O-->>A: 401 expired

How to read it

  1. Steps 1–4: a token made for orders is useless at payroll. That's what aud is for.
  2. Steps 5–6: editing the payload breaks the Ed25519 signature. Services hold only the public key, so even a hacked service can't mint tokens.
  3. Steps 7–9: Priya, HR, on a healthy company laptop: allowed.
  4. Steps 10–12: the MDM reports a problem and the very next request is blocked, though her token is still valid.
  5. Steps 13–15: fixed laptop, access back, no login needed.
  6. Steps 16–17: every stolen internal token dies on its own within 60 seconds.

Logout works the same way at the edge: the opaque token is deleted, so the next request through the gateway is a 401 at once.
