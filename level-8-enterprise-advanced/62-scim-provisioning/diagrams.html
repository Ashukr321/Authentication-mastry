How to read it

  1. The token decides the tenant. One token per customer, stored only as a hash.
  2. Every id is checked against that tenant. Another company's user looks exactly like a missing one.
  3. A duplicate create is a 409 uniqueness, which Okta and Entra ID understand.
  4. PATCH (yellow) is where IdPs differ: no-path objects, "Replace", the string "False". We apply ops to a copy, then validate the copy like a new user.
  5. The key box is green "ALL sessions ended": a leaver loses access now, not when the cookie expires.

Every box here was hit in the demo's curl run in the README.

2. Data flow: joiner, mover, leaver

Priya's whole life at TechCorp as real SCIM calls from Okta to ChaiDesk (localhost:3062), and what her browser sees.

sequenceDiagram
    autonumber
    participant O as Okta (TechCorp)
    participant S as ChaiDesk SCIM API
    participant B as Priya's browser

    Note over O,S: Joiner. Every call has Authorization Bearer scim-techcorp-...
    O->>S: GET /Users?filter=userName eq "priya@techcorp.com"
    S-->>O: 200 ListResponse totalResults 0
    O->>S: POST /Users userName, name Priya Sharma, active true
    S-->>O: 201 id 85f6d03d..., Location /scim/v2/Users/85f6d03d...
    Note over O: Okta stores id 85f6d03d... for every later call
    B->>S: POST /sso/login (after Okta SSO)
    S-->>B: sid cookie (HttpOnly), roles member

    Note over O,S: Mover
    O->>S: POST /Groups "ChaiDesk Admins", members [85f6d03d...]
    S-->>O: 201 group 3f7c0029...
    B->>S: GET /admin/reports
    S-->>B: 200 activeUsers 2 (admin via group)
    O->>S: PATCH /Groups/3f7c0029... remove members[value eq "85f6d03d..."]
    B->>S: GET /admin/reports
    S-->>B: 403 only ChaiDesk Admins
    O->>S: PATCH /Users/85f6d03d... title Team Lead, familyName Kapoor
    S-->>O: 200 version W/"2"

    Note over O,S: Leaver. IT clicks Deactivate
    O->>S: PATCH /Users/85f6d03d... op replace, value active false
    Note over S: active true to false, so end 1 session
    S-->>O: 200 active false
    B->>S: GET /me (old sid cookie)
    S-->>B: 401 Not signed in
    B->>S: POST /sso/login
    S-->>B: 403 account is deactivated

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–4: Okta always searches first, then creates. Our id is what Okta uses from then on.
  3. Steps 5–6: SSO proves who Priya is; ChaiDesk still checks she is provisioned and active.
  4. Steps 7–12: group membership becomes a role, computed on every request, so removal works on her next click.
  5. Steps 13–14: a mover's new title and surname arrive by PATCH; version goes up.
  6. Steps 15–20: the leaver. One PATCH, and her existing session is gone along with any new login.

Entra ID sends the same leaver PATCH as {"op":"Replace","path":"active","value":"False"}, and only every 40 minutes or so.
