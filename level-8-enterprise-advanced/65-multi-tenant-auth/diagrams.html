1. Flow diagram

Every check a request goes through on the safe routes, from the subdomain down to the database filter.

Safe outcome Data leaks (vulnerable route) Client-controlled: never trust it alone 
flowchart TD
    A(["Request to acme.localhost"]) --> B{"Subdomain is a<br/>known tenant?"}
    B -- No --> OK1[/"404 Unknown workspace"/]
    B -- Yes --> C{"Valid bearer token?<br/>sha256 found, not expired"}
    C -- No --> OK2[/"401 Not signed in"/]
    C -- Yes --> D{"Token's tenant ==<br/>request's tenant?"}
    D -- No --> OK3[/"401 Token is for a<br/>different workspace"/]
    D -- Yes --> E{"Tenant active and user<br/>STILL a member here?"}
    E -- No --> OK4[/"403 suspended / not a member"/]
    E -- Yes --> F["role = membership role<br/>in THIS tenant"]
    F --> G{"Route needs admin?"}
    G -- "Yes, role is member" --> OK5[/"403 Only admins of this tenant"/]
    G -- "No, or role is admin" --> H["Query WHERE tenant_id = token's tenant"]
    H --> OK6[/"Only this tenant's rows<br/>other tenants' ids give 404"/]

    V(["Vulnerable routes"]) --> X{"X-Tenant header<br/>or id with no tenant filter"}
    X --> E1[/"Another company's invoices leak"/]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class E1 error
    class OK1,OK2,OK3,OK4,OK5,OK6 ok
    class X trap

How to read it

  1. The subdomain is only a lookup key. An unknown one stops the request at once.
  2. A token is valid for one tenant. A real Zenith token on Acme's subdomain is refused.
  3. Membership and tenant status are checked on every request, so "remove member" and "suspend tenant" work instantly.
  4. The role comes from the membership in this tenant, never from the user alone.
  5. Every query is filtered by the tenant from the token. Another tenant's row looks exactly like a missing one: 404.
  6. The yellow box is the bug: a tenant id the client chose (header) or no tenant filter at all.

Every box here was hit in the demo's curl run in the README.

2. Data flow: cross-tenant attacks

Vikram (admin of Zenith) tries three ways into Acme's invoices, with the real replies from our run.

sequenceDiagram
    autonumber
    actor V as Vikram
    participant Z as zenith.localhost
    participant A as acme.localhost

    V->>A: POST /login (Vikram's correct password)
    A-->>V: 401 Wrong email or password (not an Acme member)
    V->>Z: POST /login (Vikram's correct password)
    Z-->>V: 200 token for tenant zenith, role admin, 30 min
    V->>A: GET /invoices (Bearer Zenith token)
    A-->>V: 401 This token is for a different workspace ✓
    Note over V,Z: ❌ Bug 1: tenant taken from a header
    V->>Z: GET /vulnerable/invoices, X-Tenant acme
    Z-->>V: 200 inv_101 Sharma Stores, inv_102 Gupta and Sons 😱
    Note over V,Z: ❌ Bug 2: lookup by id with no tenant filter
    V->>Z: GET /vulnerable/invoices/inv_102
    Z-->>V: 200 tenantId t_1, amount ₹1,20,000 😱
    Note over V,Z: ✅ Safe route adds AND tenant_id = t_2
    V->>Z: GET /invoices/inv_102
    Z-->>V: 404 Invoice not found ✓
    V->>Z: GET /invoices/inv_201
    Z-->>V: 200 Mehta Fabrics, ₹8,500 (his own)

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2: a correct password isn't enough. No Acme membership, no Acme login (and the error doesn't say why).
  3. Steps 5–6: a real token, but for the wrong tenant.
  4. Steps 7–8: the vulnerable route asks the client which tenant it is. Vikram just writes "acme".
  5. Steps 9–10: cross-tenant IDOR. The id is all it needs, so any guessed or leaked id works.
  6. Steps 11–14: the safe route answers 404 for Acme's invoice, exactly like a missing one.

3. Data flow: switching workspaces

Priya is admin in Acme, member in Zenith and Nimbus. Switching gives a new token, and every check runs again.

sequenceDiagram
    autonumber
    actor P as Priya
    participant A as acme.localhost
    participant Z as zenith.localhost

    P->>A: POST /login (Priya's password)
    A-->>P: 200 token for acme, role admin, 8 hours
    P->>A: GET /workspaces
    A-->>P: acme (admin), zenith (member), nimbus (member)
    P->>A: POST /switch, tenant zenith
    Note over A: member of zenith? yes. active? yes. password login allowed? yes
    A-->>P: 200 NEW token for zenith, role member, 30 min
    P->>Z: GET /members (Zenith token)
    Z-->>P: 403 Only admins of Zenith Textiles ✓
    P->>A: GET /members (Acme token)
    A-->>P: 200 Priya admin, Rahul member
    P->>A: POST /switch, tenant nimbus
    Note over A: Nimbus policy says SSO only
    A-->>P: 403 requires sign-in through its company SSO ✓
    P->>A: DELETE /members/Rahul's account
    A-->>P: 200 removed, Rahul's Acme tokens deleted
    P->>Z: POST /logout (Zenith token)
    Z-->>P: 200 Logged out (the Acme token still works)

How to read it

  1. Steps 1–4: one identity, one login, but the token is for Acme only. The picker lists only her own memberships.
  2. Steps 5–7: switching issues a new token after checking membership, status and Zenith's own policy (shorter tokens).
  3. Steps 8–11: the same person is admin in one tenant and a member in another.
  4. Steps 12–14: Nimbus's "SSO only" rule can't be skipped by switching from a password session.
  5. Steps 15–18: removal and logout are per tenant. Nothing in one tenant changes another.

Not shown: OldCo is suspended, so even Meera's correct password gets a 403.
