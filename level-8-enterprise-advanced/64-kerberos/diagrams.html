How to read it

  1. The AS only issues a TGT if the pre-auth timestamp opens with the user's key. That's the one moment the password matters.
  2. The TGS checks the TGT and the authenticator, but not permissions (yellow). That's by design, and it's what makes Kerberoasting possible.
  3. The service checks everything with its own keytab key: right service, not expired, fresh, not replayed. It never calls the KDC.
  4. Authorization comes last, from the groups (PAC) inside the ticket.
  5. The two red boxes are the attacks the protocol can't stop by itself: weak service passwords and stolen ticket caches.

Every box here was hit in the README's curl run.

2. Data flow

The three exchanges with the real messages from our demo. { … }key means "encrypted with that key".

sequenceDiagram
    autonumber
    actor R as Rahul (kinit, ccache)
    participant K as KDC (AS + TGS)
    participant P as Payroll service (keytab)

    Note over R: password chai-and-code-42 becomes rahulKey, password forgotten
    R->>K: POST /kdc/as cname rahul, nonce, padata {ts}rahulKey
    Note over K: opens padata with stored rahulKey, time within 5 min
    K-->>R: ticket TGT {rahul, S1, groups}krbtgtKey + encPart {S1, nonce}rahulKey
    Note over R: opens encPart, nonce matches, saves TGT + S1 in rahul.ccache

    R->>K: POST /kdc/tgs TGT + authenticator {rahul, ctime}S1 + sname HTTP/payroll
    Note over K: opens TGT with krbtgtKey, gets S1, checks authenticator
    K-->>R: ticket {rahul, S2, groups Employees}payrollKey + encPart {S2, nonce}S1

    R->>P: GET /payroll/me, Authorization Negotiate (ticket + {rahul, ctime}S2)
    Note over P: opens ticket with keytab, gets S2, checks authenticator, no KDC call
    P-->>R: 200 salary 18 lakh + WWW-Authenticate Negotiate {ctime}S2
    Note over R: AP-REP opens with S2, so the server is genuine (mutual auth)

    R->>P: same Authorization header again (replay)
    P-->>R: 401 KRB_AP_ERR_REPEAT

How to read it

  1. Each column is one machine. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2 (AS): only an encrypted timestamp goes out. The reply has two envelopes: one for the KDC itself (TGT), one for Rahul (S1).
  3. Steps 3–4 (TGS): no password. The authenticator proves Rahul holds S1. The new ticket is locked with payroll's key, so Rahul can't read or change it.
  4. Steps 5–6 (AP): payroll opens the ticket with its keytab, learns S2, checks the authenticator. The reply's AP-REP proves payroll is real.
  5. Steps 7–8: a captured header is useless a second time.

S1 = TGS session key, S2 = payroll session key. Both are random and new for every logon / ticket.

3. Who opens what

Kerberos is envelopes inside envelopes. Each key opens one envelope, and that envelope holds the next key.

Key Rahul holds Key only the KDC holds Key the KDC and the service hold 
flowchart LR
    RK["rahul's key<br/>(from his password)"] -- opens --> ASREP["AS-REP encPart"]
    KT["krbtgt key"] -- opens --> TGT["TGT"]
    ASREP -. "holds" .-> S1["S1<br/>TGS session key"]
    TGT -. "holds" .-> S1
    S1 -- opens --> TGSREP["TGS-REP encPart"]
    PK["payroll key<br/>(keytab)"] -- opens --> ST["Service ticket"]
    TGSREP -. "holds" .-> S2["S2<br/>payroll session key"]
    ST -. "holds" .-> S2
    S2 -- opens --> AUTH["Authenticator + AP-REP"]

How to read it

  1. Rahul gets S1 by opening the AS-REP with his own key; the KDC gets the same S1 by opening the TGT with the krbtgt key. Now both share S1.
  2. Same trick one level down: Rahul gets S2 from the TGS-REP (with S1); payroll gets S2 from the service ticket (with its keytab).
  3. Steal the krbtgt key → make any TGT (golden ticket). Steal or crack the payroll key → make any payroll ticket (silver ticket).
  4. Steal Rahul's ccache → you have tickets and S1/S2, so you are Rahul until they expire (pass-the-ticket).

Rahul never learns the krbtgt or payroll key, and payroll never learns Rahul's key.
