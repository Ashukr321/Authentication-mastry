How to read it

  1. The email domain picks the org, the org picks the IdP. No org means plain password login, unless the org enforces SSO.
  2. Discovery is checked before anyone is sent away: Umbrella's missing / fails here, once, with a clear log line.
  3. The state remembers which org the login started with. From then on the callback trusts only that, never the token's own iss.
  4. A code from another IdP fails at this org's token endpoint (mix-up). A bad token fails the ID token checks from topic 36.
  5. Yellow: email_verified: true from a customer's IdP is just that customer's admin talking. The verified-domain check is the real trust boundary.
  6. Users are found by (org, subject); the role is recomputed on every login.

Every box here was hit in the README's curl run.

    O-->>R: 302 to /sso/callback?code=...&state=...
    R->>K: GET /sso/callback?code=...&state=...
    Note over K: state found in this session, so the org is Acme
    K->>O: POST /v1/token (Basic client auth, code, code_verifier)
    O-->>K: id_token: iss okta/oauth2/default, sub 00u8rahul1a2b3c4d5, groups KaamKaro-Admins
    K->>O: GET /v1/keys (once, cached by kid)
    Note over K: RS256 ok, iss and aud are Acme's, nonce ok, domain acme.example verified for Acme
    K-->>R: 303 /me, new session. Linked to usr_kYuCMw, role admin

    Note over R,S: 😈 Vikram, through Shady Ltd's connection
    R->>K: POST /sso/start, email at shady.example
    K-->>R: 303 to Shady's Keycloak
    R->>S: log in as vikram
    S-->>K: (via callback + token) id_token signed by Shady: email of Rahul at acme.example, email_verified true
    Note over K: signature, iss, aud, nonce all VALID for Shady. But acme.example is not Shady's domain
    K-->>R: 403 Shady Ltd's sign-in can't be used for acme.example accounts

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–5: the email chose Acme; KaamKaro read Okta's endpoints from discovery and remembered "this state is Acme".
  3. Steps 6–9: the user logs in at Okta, never at KaamKaro. MFA and company rules happen there.
  4. Steps 10–13: the code is swapped at Acme's token endpoint, and the ID token is checked against Acme's issuer, client id and keys.
  5. Step 14: Rahul's old password account is linked, and his role comes from the groups claim.
  6. Steps 15–19: Shady's token is cryptographically perfect. It fails only on the business rule: Shady never proved it owns acme.example.

3. Four IdPs, one shape

The same protocol, four different ID token layouts. A tiny claim profile per IdP type turns each into { subject, email, groups }, and everything after that is shared code.

The common shape KaamKaro uses Quirk that breaks naive code

How to read it

  1. Left: the parts of each ID token that differ. Everything else (aud, exp, nonce, RS256) is identical.
  2. Yellow: the three quirks that most often break hand-written integrations.
  3. Middle: the claim profile is the only IdP-specific code in KaamKaro: four one-line functions.
  4. Right: the user is keyed by org + subject (Entra: oid), and the app role comes from the group the org's admin picked.

The issuer shapes shown are the demo's; in real life they're acme.okta.com/oauth2/default, login.microsoftonline.com/TENANT/v2.0, globex.auth0.com/ and sso.initech.com/realms/initech.
