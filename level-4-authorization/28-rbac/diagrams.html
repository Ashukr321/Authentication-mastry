1. Flow diagram

Every protected request asks two questions, in this order: who are you, and are you allowed?

Route runs 401 / 403 Where beginners slip 
flowchart TD
    A(["POST /admin/orders/ord_1/refund<br/>Authorization: Bearer token"]) --> T{"requireAuth:<br/>token valid?"}
    T -- "No: missing, expired" --> U[/"401 Please log in"/]
    T -- Yes --> L["Load the user FRESH from the database<br/>(roles too, never from the request)"]
    L --> P["requirePermission orders:refund<br/>permissions = union of the user's roles"]
    P --> H{"has orders:refund?"}
    H -- "No: customer, editor" --> F[/"403 You don't have permission<br/>+ log who was denied"/]
    H -- "Yes: support, admin" --> OK[/"✅ refund runs<br/>+ audit log"/]
    OK --> O["Next check, if the route needs it:<br/>is this row yours? (topic 31)"]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class U,F error
    class OK ok
    class L,O trap

How to read it

  1. 401 means "I don't know who you are". 403 means "I know you, and no".
  2. Roles are loaded from your database on every request, so a role change works at once. Never read them from the body or a header.
  3. The route asks for a permission, not a role name. Any role that bundles orders:refund passes.
  4. RBAC checks the action. Whether the row belongs to you is a separate check (topic 31).

2. Data flow

Three users with the same kind of token hit the same routes, then Amit changes Rahul's roles.

sequenceDiagram
    autonumber
    actor R as Rahul (customer)
    actor P as Priya (support)
    actor A as Amit (admin)
    participant API as Shop API
    participant DB as Database

    R->>API: POST /admin/orders/ord_1/refund (Bearer Rahul's token)
    API->>DB: user u_rahul has roles?
    DB-->>API: [customer] gives products:read
    API-->>R: 403 You don't have permission to do this
    P->>API: POST /admin/orders/ord_1/refund (Bearer Priya's token)
    API->>DB: user u_priya has roles?
    DB-->>API: [support] gives orders:refund
    API-->>P: 200 status refunded
    P->>API: PUT /admin/users/u_rahul/roles {"roles":["admin"]}
    API-->>P: 403 (support has no users:manage)
    A->>API: PUT /admin/users/u_rahul/roles {"roles":["customer","editor"]}
    API->>DB: save roles of u_rahul
    API-->>A: 200 permissions products:read, products:write
    R->>API: POST /products {"name":"Ginger chai","price":260} (same old token)
    API->>DB: user u_rahul has roles?
    DB-->>API: [customer, editor] gives products:write
    API-->>R: 201 product created
    Note over R,API: no re-login needed, because roles are read from the database, not from the token

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–4: Rahul is logged in (no 401) but a customer can't refund: 403.
  3. Steps 5–8: the same call from Priya works, because her role bundles orders:refund.
  4. Steps 9–10: support can refund but can't hand out roles. Only users:manage can.
  5. Steps 11–17: Amit adds the editor role. Rahul's very next request with the same token can add products. If roles lived inside a JWT, he would have to wait for a new token.

3. The model

Users get roles, roles get permissions. Code only ever looks at the permissions on the right.

Permission (what routes check) Role (a job title, a bundle)

In a database this is five tables: users, roles, permissions, user_roles and role_permissions. A new role like finance is new rows, not new code in every route.
