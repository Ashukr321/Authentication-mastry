1. Flow diagram

What the server checks, in order, for every request that carries an API key.

How to read it

  1. Keys in URLs leak into logs, so they're refused before anything else.
  2. The server never stored the key, only its hash, so it hashes what it receives and looks that up.
  3. Unknown, revoked and expired all give the same 401.
  4. Then three separate questions: how often (429), what (scope, 403), and whose data (owner, topic 31).
  5. The log names the key id, so you know which integration did what.

2. Data flow

One key's whole life: Rahul creates it, his POS machine uses it, then he rotates it.

sequenceDiagram
    autonumber
    actor R as Rahul (dashboard)
    participant POS as POS machine
    participant API as Shop API
    participant DB as api_keys table

    R->>API: POST /keys (Bearer session) name POS machine, scopes read + write
    API->>DB: save sha256(key), id key_a612, hint chai_key_kSmY…1s0o
    API-->>R: 201 the full key, shown ONCE
    R->>POS: put the key in the POS config (secret store, not Git)
    POS->>API: POST /api/orders (X-API-Key)
    API->>DB: find sha256(key), update lastUsedAt
    API-->>POS: 201 order created
    POS->>API: 10 more requests in the same minute
    API-->>POS: 429 Retry-After 59
    Note over R,DB: rotation, with no downtime
    R->>API: POST /keys (new POS key)
    API-->>R: 201 new key, shown once
    R->>POS: switch the config to the new key
    R->>API: GET /keys, old key's lastUsedAt has stopped changing
    R->>API: DELETE /keys/key_a612
    API->>DB: set revokedAt
    POS->>API: a request with the OLD key (an old copy somewhere)
    API-->>POS: 401 Invalid API key

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–3: a logged-in person creates the key. The database gets only the hash.
  3. Steps 4–7: the program sends the key in a header; the server updates lastUsedAt.
  4. Steps 8–9: the per-key rate limit protects the API from one runaway script.
  5. Steps 10–17: rotation. Two keys work at the same time until the old one is revoked, and revoking takes effect at once.

A database leak gives attackers hashes of 256-bit random values: useless. That's why a fast SHA-256 is fine here, while passwords need a slow hash.
