1. Flow diagram

Any request that carries an id: the owner comes from the token, and goes into the lookup.

Allowed Stopped Where beginners slip 
flowchart TD
    A(["PATCH /orders/ord_1002<br/>Bearer Rahul's token<br/>body: address"]) --> AU{"Logged in?"}
    AU -- No --> U[/"401 Please log in"/]
    AU -- "Yes: req.user = u_rahul" --> Q["findOrder(ord_1002, owner = u_rahul)<br/>WHERE id = $1 AND user_id = $2"]
    Q --> F{"Found?"}
    F -- "No: missing OR someone else's" --> N[/"404 Order not found<br/>+ log the attempt"/]
    F -- Yes --> W{"Only allowed fields?<br/>(address, phone)"}
    W -- "No: total, status, userId" --> B[/"400 You can't change: total"/]
    W -- Yes --> S{"Right state?<br/>(not shipped yet)"}
    S -- No --> C[/"409 Order has already shipped"/]
    S -- Yes --> OK[/"✅ update the order"/]
    A -. "IDOR: findById(ord_1002) only" .-> LEAK["Sneha's order loaded and changed"]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12

    class LEAK,Q trap

How to read it

  1. The owner is req.user.id from the token. Nothing in the URL, body or query decides who the owner is.
  2. The yellow lookup is the heart of it: the owner is part of the query, so someone else's record never comes back.
  3. "Missing" and "not yours" give the same 404. The server logs which one it was.
  4. For writes, two more checks: only allowed fields, and the record is in a state where the change makes sense.
  5. The dotted line is IDOR: load by id alone, and every record is reachable.

2. Data flow

Rahul is a real, logged-in customer. He just changes the number in the URL.

    R->>BUG: GET /buggy/orders/ord_1002
    BUG->>DB: find by id ord_1002
    DB-->>BUG: Sneha's order
    BUG-->>R: 200 saree, 18500, 7 Lodhi Colony, phone
    R->>BUG: GET /buggy/orders?userId=u_sneha
    BUG-->>R: 200 Sneha's whole order history
    R->>BUG: PATCH /buggy/orders/ord_1001 total 1, status delivered
    BUG-->>R: 200 his own order now costs 1 rupee
    Note over R,LOG: the same requests against the fixed API
    R->>API: GET /orders/ord_1002
    API->>DB: find ord_1002 where owner is u_rahul
    DB-->>API: nothing
    API->>LOG: u_rahul tried GET ord_1002, which belongs to u_sneha
    API-->>R: 404 Order not found
    R->>API: GET /orders?userId=u_sneha
    API-->>R: 200 only Rahul's orders (the query parameter is ignored)
    R->>API: PATCH /orders/ord_1001 total 1, status delivered
    API-->>R: 400 You can't change total, status

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–4: the classic IDOR. Login worked perfectly, and it didn't matter.
  3. Steps 5–6: the owner taken from the query string instead of the token.
  4. Steps 7–8: mass assignment on his own order: ownership alone isn't enough for writes.
  5. Steps 9–17: the fixed API scopes every lookup to the token's user, answers 404, logs the probe, and accepts only editable fields.

3. The checklist

Every place a client can name a record needs the same check. IDOR hides in the ones people forget.

Often forgotten The check 
flowchart LR
    ID(["An id from the client"]) --> G["GET /orders/:id"]
    ID --> W["PATCH, PUT, DELETE<br/>/orders/:id"]
    ID --> L["Lists and filters<br/>?userId=, ?ids="]
    ID --> NE["Nested routes<br/>/orders/:id/items/:itemId"]
    ID --> BO["Ids inside the body<br/>orderId, addressId"]
    ID --> FI["Files and downloads<br/>invoice_1002.pdf"]
    ID --> BA["GraphQL, batch, export"]
    G --> CK["owner = req.user.id<br/>in the query, 404 if not found"]
    W --> CK
    L --> CK
    NE --> CK
    BO --> CK
    FI --> CK
    BA --> CK

Test it the way attackers do: log in as two users, take user A's ids, and call every endpoint as user B. Random ids (UUIDs) make guessing harder, but the check is still the fix.
