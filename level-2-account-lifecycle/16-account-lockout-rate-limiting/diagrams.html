1. Flow diagram

The order of checks on POST /login. The cheap checks come first, and the expensive password hash comes last.

Logged in Refused Lock starts: the wait doubles each time Counters (Redis in production) 
flowchart TD
    A(["POST /login<br/>{ email, password }"]) --> IP[("IP counter + 1")]
    IP --> Q1{"More than 20<br/>this minute?"}
    Q1 -- Yes --> E1[/"429 Too many requests<br/>Retry-After: 36"/]
    Q1 -- No --> Q2{"This email<br/>locked right now?"}
    Q2 -- "Yes (even if the<br/>password is right)" --> E2[/"429 Too many failed attempts<br/>Retry-After: 5"/]
    Q2 -- No --> H["scrypt check<br/>(dummy hash if no account)"]
    H --> Q3{"Password right?"}
    Q3 -- Yes --> RS["Reset failures<br/>and backoff"]
    RS --> OK[/"200 Logged in"/]
    Q3 -- No --> F["failures + 1<br/>(for the typed email,<br/>account or not)"]
    F --> Q4{"5 failures?"}
    Q4 -- No --> E3[/"401 Invalid email or password"/]
    Q4 -- Yes --> L["Lock for 1, 2, 4… min<br/>(max 1 hour)<br/>email the real owner"]
    L --> E3

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class E1,E2,E3 error
    class OK ok
    class L trap

How to read it

  1. Layer 1 (top): the IP limit runs before anything else, so a flood never reaches the expensive hash.
  2. Layer 2: a locked email is refused before the password is checked, so even the right password gets 429.
  3. Failures are counted for the typed email, so accounts that don't exist lock the same way (no enumeration).
  4. The yellow box: each new lock is twice as long. It never lasts forever, so attackers can't lock real users out for good.
  5. A correct password resets the counters.

2. Data flow

Priya guesses Rahul's password. His account locks, Rahul gets an email, and Priya's script then hits the per-IP limit.

sequenceDiagram
    autonumber
    actor A as Priya's script (IP 203.0.113.7)
    participant S as Server
    participant R as Counters
    participant M as Rahul's inbox

    loop 5 times
        A->>S: POST /login { rahul@mail.com, "guess" }
        S->>R: ip 203.0.113.7 + 1 (under 20 ✓), email not locked ✓
        S->>R: failures("rahul@mail.com") + 1
        S-->>A: 401 Invalid email or password
    end
    S->>R: 5 failures → lockedUntil = now + 1 min
    S->>M: "Someone is trying to log in to your account"
    A->>S: POST /login { rahul@mail.com, "correct horse battery" }
    S->>R: email locked for 60 s
    S-->>A: 429 Retry-After: 60 (even the right password)
    A->>S: POST /login { priya@mail.com, "Password@123" } … 14 more emails
    S-->>A: 401 401 401 …
    A->>S: POST /login (request 21 this minute)
    S->>R: ip 203.0.113.7 = 21, over 20
    S-->>A: 429 Too many requests (RateLimit-Remaining: 0, Retry-After: 36)

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. The loop: 5 wrong guesses. Each one counts against the IP and the email.
  3. After the 5th, the email is locked and the real owner gets an email. The script gets nothing extra.
  4. Even a correct guess now gets 429, so the script can't tell it guessed right.
  5. The script switches to other accounts (password spraying). The account locks don't help here, but the per-IP limit stops it after 20 tries.

Two common attacks. Each one is stopped by a different layer.

Attacks from a botnet (thousands of IPs, a few tries each) get past both layers. That's where MFA, breached-password checks, CAPTCHA and bot detection come in.
