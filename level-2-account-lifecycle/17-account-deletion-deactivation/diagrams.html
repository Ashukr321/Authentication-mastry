1. Flow diagram

Every check the server does when Rahul presses "Delete my account"

Done Rejected Waiting: can still be undone Database 
flowchart TD
    A(["POST /account/delete<br/>{ password, confirm }"]) --> S{"Valid session and<br/>status = active?"}
    S -- No --> E1[/"401 Not logged in"/]
    S -- Yes --> C{"confirm = DELETE?"}
    C -- No --> E2[/"400 Type DELETE to confirm"/]
    C -- Yes --> P{"Password correct?<br/>(re-authentication)"}
    P -- No --> E3[/"403 Wrong password"/]
    P -- Yes --> M[("status = pending_deletion<br/>deleteAfter = now + 30 days")]
    M --> L["Delete ALL sessions:<br/>every device logged out"]
    L --> N["Email: your account<br/>will be deleted"]
    N --> W[/"202 Accepted<br/>grace period starts"/]
    W --> G{"Logs in again<br/>before deleteAfter?"}
    G -- Yes --> X[/"Deletion cancelled<br/>status = active"/]
    G -- No --> J["Purge job: erase personal data,<br/>tokens, files, third-party copies"]
    J --> K[/"Account erased<br/>audit log keeps the id only"/]

How to read it

  1. Only a logged-in, active user gets past the first check.
  2. Typing DELETE stops mis-clicks. The password stops someone with a stolen session cookie.
  3. Nothing is erased yet: the row is only marked (soft delete) and every device is logged out.
  4. The yellow box is the grace period. Logging in with the password cancels it.
  5. When it ends, a background job really erases the data. Only an anonymous record stays.

2. Data flow

Rahul deactivates, comes back, then deletes his account for good. His phone is logged in the whole time.

sequenceDiagram
    autonumber
    participant L as Rahul's laptop
    participant P as Rahul's phone
    participant S as Server
    participant DB as Database
    participant J as Purge job

    L->>S: POST /account/deactivate { password: "rahul password 123" }
    S->>DB: verify password ✓, UPDATE u_1 SET status = "deactivated"
    S->>DB: DELETE all sessions of u_1
    S-->>L: 200 Account deactivated (+ email notice)
    P->>S: GET /me (sid=9c1e…)
    S-->>P: 401 Not logged in
    L->>S: POST /login { email, password }
    S->>DB: password ✓, status = "active"
    S-->>L: 200 { notice: "Welcome back! Your account is active again." }
    L->>S: POST /account/delete { password, confirm: "DELETE" }
    S->>DB: status = "pending_deletion", deleteAfter = +30 days
    S->>DB: DELETE all sessions of u_1
    S-->>L: 202 { deleteAfter: "2026-12-05T..." } (+ email notice)
    Note over L,J: 30 days pass, Rahul doesn't log in
    J->>DB: find pending_deletion with deleteAfter in the past
    J->>DB: DELETE user u_1, tokens, files. Orders: name → "Deleted user"
    J->>DB: INSERT audit { event: "account_erased", userId: u_1 }
    L->>S: POST /login { email, password }
    S-->>L: 401 Invalid email or password

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–6: deactivating only changes the status and logs out every device, the phone included.
  3. Steps 7–9: logging in with the right password reactivates the account.
  4. Steps 10–13: deleting is a soft delete with a date. Nothing is erased yet.
  5. Steps 14–17: the purge job, not the request, erases the data and keeps an id-only audit entry.
  6. Steps 18–19: the account no longer exists, so login gives the normal "invalid" reply.

3. Account states

One status field, four states. Only active users count as logged in.

Can log in and use the app Switched off: data kept, can come back Gone for good 
flowchart LR
    SU(["Sign up"]) --> A["active"]
    A -- "deactivate<br/>(password)" --> D["deactivated<br/>data kept, hidden"]
    D -- "log in<br/>(password)" --> A
    A -- "delete<br/>(password + DELETE)" --> PD["pending_deletion<br/>grace period"]
    PD -- "log in before<br/>deleteAfter" --> A
    PD -- "purge job after<br/>deleteAfter" --> X["erased<br/>email free again"]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class A ok
    class D,PD trap
    class X error

How to read it

  1. Every arrow out of active needs the password again and logs out every device.
  2. deactivated and pending_deletion both lead back to active by logging in.
  3. Only the purge job moves an account to erased, and there's no way back.
  4. An admin "banned" status (Level 7) would be a fifth state that logging in can not undo.

Erasing means everywhere: sessions and tokens (topics 09, 13, 15), uploads, analytics and email tools. Orders and invoices the law makes you keep are anonymized, not deleted.
