1. Flow diagram

What the server checks on POST /change-password { currentPassword, newPassword }

Success Error: nothing changes Sessions deleted: can't be undone User / session store 
flowchart TD
    A(["Rahul presses Save<br/>Cookie: sid=3016…"]) --> L{"Logged in?"}
    L -- No --> E0[/"401 Not logged in"/]
    L -- Yes --> K{"Locked after 5<br/>wrong tries?"}
    K -- Yes --> E1[/"429 Too many wrong attempts<br/>try again in 15 minutes"/]
    K -- No --> C{"currentPassword<br/>matches the hash?"}
    C -- "No: count +1" --> E2[/"403 Current password<br/>is incorrect"/]
    C -- Yes --> N{"newPassword OK?<br/>8-128 chars, not common,<br/>not the email, not the same"}
    N -- No --> E3[/"400 Bad Request<br/>the reason"/]
    N -- Yes --> H[("Save new hash<br/>passwordChangedAt = now")]
    H --> X["Delete every OTHER session<br/>of this user"]
    X --> R["Delete this session too,<br/>create a NEW one + Set-Cookie"]
    R --> M["Email: Your password was changed"]
    M --> OK[/"200 OK<br/>Password changed"/]

How to read it

  1. Start at the top: Rahul is on the Change password page and presses Save.
  2. Diamonds are questions the server asks, in this order. Each red box stops everything.
  3. The lockout is checked first, so a session thief can't keep guessing the current password.
  4. The current password is checked before the new one, so nobody learns anything without knowing it.
  5. The yellow boxes: other devices are logged out, and this device gets a new session ID.

Wrong current password → 403, not 401. The user is still logged in, and a 401 would make most frontends send them to the login page.

2. Data flow

Rahul is logged in on a laptop and a phone. Priya has a copy of the laptop's cookie. Rahul changes his password on the laptop.

sequenceDiagram
    autonumber
    participant L as Rahul's laptop
    participant P as Rahul's phone
    actor A as Priya (copied cookie)
    participant S as Server
    participant DB as Database
    participant M as Email inbox

    Note over L,DB: Sessions: laptop sid=3016…, phone sid=b71c… (Priya has a copy of 3016…)
    L->>S: POST /change-password { currentPassword: "old…", newPassword: "new password 456" }
    S->>DB: Find session sha256("3016…") → user u_1
    S->>DB: scrypt("old…") matches passwordHash ✓
    Note over S: New password: long enough, not common, not the same ✓
    S->>DB: UPDATE u_1 SET passwordHash = scrypt(new), passwordChangedAt = now
    S->>DB: DELETE sessions of u_1 except sha256("3016…") (the phone)
    S->>DB: DELETE sha256("3016…"), INSERT sha256("d698…")
    S->>M: "Your password was changed"
    S-->>L: 200 + Set-Cookie: sid=d698… { otherDevicesLoggedOut: 1 }
    A->>S: GET /me (Cookie: sid=3016…)
    S-->>A: 401 Not logged in ✓
    P->>S: GET /me (Cookie: sid=b71c…)
    S-->>P: 401 Not logged in ✓
    L->>S: GET /me (Cookie: sid=d698…)
    S-->>L: 200 still logged in

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Step 3: the session alone isn't trusted. The current password is checked again.
  3. Step 4: only the new hash is saved, never the password.
  4. Steps 5–6: the phone's session is deleted, and the laptop's session is replaced with a new ID.
  5. Steps 9–12: Priya's copy and the phone are both out. Only the laptop, with its new cookie, is still in (steps 13–14).
