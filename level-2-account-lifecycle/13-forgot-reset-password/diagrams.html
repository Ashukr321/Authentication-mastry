1. Flow diagram

What the server checks when the new password is submitted: POST /reset-password { token, newPassword }

Success Error: the server stops here Token deleted / devices logged out: can't be undone Token store 
flowchart TD
    A(["User presses Save on the form<br/>POST /reset-password { token, newPassword }"]) --> B{"Token has<br/>64 hex characters?"}
    B -- No --> E1[/"400 Bad Request<br/>This link is invalid or has expired"/]
    B -- Yes --> P{"New password<br/>8-128 characters?"}
    P -- No --> E2[/"400 Bad Request<br/>The new password must be 8-128 characters<br/>(token NOT used, try again)"/]
    P -- Yes --> C["key = sha256(token)"]
    C --> D[("Look up the key<br/>in the token store")]
    D --> F{"Found?"}
    F -- "No: never existed,<br/>or already used" --> E1
    F -- Yes --> X["Delete the token NOW<br/>(single use)"]
    X --> G{"Expired?<br/>older than 15 min"}
    G -- Yes --> E1
    G -- No --> H["passwordHash = scrypt(newPassword)<br/>passwordChangedAt = now"]
    H --> L["Delete ALL reset tokens<br/>and ALL sessions of this user"]
    L --> N["Email: Your password was changed"]
    N --> OK[/"200 OK<br/>Password changed. Please log in."/]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class E1,E2 error
    class OK ok
    class X,L trap

How to read it

  1. Start at the top: the user has opened the link and typed a new password.
  2. Diamonds are questions the server asks. Follow Yes or No.
  3. The password is checked before the token is used, so a too-short password doesn't waste the link.
  4. The first yellow box: the token is deleted before the expiry check, so it can never be used twice.
  5. The second yellow box: every device is logged out. If an attacker was inside, they're kicked out now.
  6. Every bad link ends in the same red box: "fake", "used" and "expired" look identical.

Opening the link (GET) only shows the form. Email scanners open links on their own, so only the POST uses the token.

2. Data flow

The whole journey: Rahul asks for a link, sets a new password, and the attacker's laptop gets logged out.

sequenceDiagram
    autonumber
    actor U as Rahul
    participant B as Browser
    participant S as Server
    participant DB as Database
    participant M as Email inbox
    actor A as Priya's laptop (attacker)

    Note over A,S: Priya stole the old password and is logged in (session sid=7c1e…)
    U->>B: Clicks "Forgot password?"
    B->>S: POST /forgot-password { email: "rahul@mail.com" }
    Note over S: token = randomBytes(32) → "8b6d…e1a7"
    S->>DB: INSERT reset token { sha256("8b6d…"), userId: "u_1", expiresAt: +15 min }
    S->>M: "Reset your password" + myapp.com/reset-password?token=8b6d…e1a7
    S-->>B: 202 "If an account exists, we've sent a reset link"
    U->>M: Opens the email, clicks the link
    M->>S: GET /reset-password?token=8b6d…e1a7
    S-->>B: 200 "Choose a new password" form (token NOT used yet)
    U->>B: Types a new password, presses Save
    B->>S: POST /reset-password { token: "8b6d…", newPassword }
    S->>DB: Find + DELETE sha256("8b6d…") (not expired ✓)
    S->>DB: UPDATE user u_1 SET passwordHash = scrypt(new)
    S->>DB: DELETE all sessions WHERE userId = "u_1"
    S->>M: "Your password was changed"
    S-->>B: 200 "Password changed. Please log in."
    A->>S: GET /me (cookie sid=7c1e…)
    S-->>A: 401 Not logged in ✓

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. Step 3: the database gets only the hash of the token. The plain token goes only into the email (step 4).
  3. Steps 7–8: opening the link just shows the form. Nothing changes yet.
  4. Step 11: the token is found and deleted in one go, so the link is single-use.
  5. Step 13: every session is deleted, so Priya's laptop is kicked out (steps 16–17).
  6. Step 14: the notice email warns Rahul if he didn't ask for the reset.

3. Forgot request: always the same reply

What happens on POST /forgot-password. Every path ends in the same answer.

Reset email sent Nothing sent, but the reply looks the same 
flowchart TD
    A(["POST /forgot-password<br/>{ email }"]) --> B{"Does the account exist?"}
    B -- No --> N["Send nothing"]
    B -- Yes --> D{"Reset email sent<br/>less than 1 min ago?"}
    D -- Yes --> N
    D -- No --> K["Delete ALL old reset tokens<br/>for this user"]
    K --> T["Create a new token<br/>and email the link<br/>(built from BASE_URL, not Host)"]
    N --> R[/"202 Accepted<br/>If an account exists for that email,<br/>we've sent a reset link."/]
    T --> R

    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class T ok
    class N trap

How to read it

  1. Two reasons to send nothing: no such account, or a reset email was sent less than a minute ago.
  2. Every path ends in the same 202 reply, so attackers can't use this page to find out who has an account.
  3. The cooldown stops attackers from using your app to flood someone's inbox.
  4. Before sending, all old reset links are deleted, so only the newest email works.
  5. The link uses your own BASE_URL. If it used the request's Host header, an attacker could make the real email point to their site.

In a real app, send the email from a background job, so "account exists" and "no account" take the same time to answer.
