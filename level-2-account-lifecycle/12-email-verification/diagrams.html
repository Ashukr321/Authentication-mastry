1. Flow diagram

What the server checks when someone clicks the link in the email: GET /verify-email?token=…

Success Error: the server stops here Token deleted: it can never be used again Token store 
flowchart TD
    A(["User clicks the link<br/>GET /verify-email?token=9f3a…"]) --> B{"Is there a token<br/>with 64 hex characters?"}
    B -- No --> E1[/"400 Bad Request<br/>This link is invalid or has expired"/]
    B -- Yes --> C["key = sha256(token)"]
    C --> D[("Look up the key<br/>in the token store")]
    D --> F{"Found?"}
    F -- "No: never existed,<br/>or already used" --> E1
    F -- Yes --> X["Delete the token NOW<br/>(single use)"]
    X --> G{"Expired?<br/>older than 24 h"}
    G -- Yes --> E1
    G -- No --> H["user.emailVerified = true<br/>user.verifiedAt = now"]
    H --> OK[/"200 OK<br/>Email verified! You can now log in."/]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class E1 error
    class OK ok
    class X trap

How to read it

  1. Start at the top: the user clicks the link from their email.
  2. Diamonds are questions the server asks. Follow Yes or No.
  3. The server hashes the token before looking it up, because only hashes are stored.
  4. The yellow box: the token is deleted before the expiry check, so it can never be used twice.
  5. Every failure ends in the same red box. The attacker can't tell "fake" from "used" from "expired".

Expiry is checked by the server using expiresAt from the store. Nothing in the link itself is trusted except the random token.

2. Data flow

The whole journey: signup creates an unverified user, the email carries the secret link, and login only works after the click.

sequenceDiagram
    autonumber
    actor U as Rahul
    participant B as Browser
    participant S as Server
    participant DB as Database
    participant M as Email inbox

    U->>B: Fills the signup form
    B->>S: POST /signup { email: "rahul@mail.com", password }
    S->>DB: INSERT user { id: "u_1", emailVerified: false }
    Note over S: token = randomBytes(32) → "9f3a…c21d"
    S->>DB: INSERT token { sha256("9f3a…"), userId: "u_1", expiresAt: +24 h }
    S->>M: "Verify your email" + myapp.com/verify-email?token=9f3a…c21d
    S-->>B: 201 { emailVerified: false, "Check your email" }
    U->>B: Tries to log in right away
    B->>S: POST /login { email, password }
    Note over S: Password correct ✓<br/>but emailVerified is false
    S-->>B: 403 "Please verify your email first"
    U->>M: Opens the email
    M->>S: GET /verify-email?token=9f3a…c21d (the click)
    S->>DB: Find + DELETE sha256("9f3a…")
    DB-->>S: { userId: "u_1", expiresAt } (not expired ✓)
    S->>DB: UPDATE user u_1 SET emailVerified = true
    S-->>B: 200 "Email verified! You can now log in."
    B->>S: POST /login { email, password }
    S-->>B: 200 Logged in ✓

How to read it

  1. Each column is one part of the system. Solid arrows are requests, dashed arrows are replies.
  2. The numbers show the order things happen.
  3. Step 5: the database gets only the hash of the token. The plain token goes only into the email (step 6).
  4. Steps 8–11: login is blocked, but only after the password is checked.
  5. Step 14: the token is found and deleted in one go, so the link is single-use.

3. Resend: only the newest link works

The user asks for a new link. The reply is always the same, and old links die.

New email sent Nothing sent, but the reply looks the same 
flowchart TD
    A(["POST /resend-verification<br/>{ email }"]) --> B{"Does the account exist?"}
    B -- No --> N["Send nothing"]
    B -- Yes --> C{"Already verified?"}
    C -- Yes --> N
    C -- No --> D{"Last email sent<br/>less than 1 min ago?"}
    D -- Yes --> N
    D -- No --> K["Delete ALL old tokens<br/>for this user"]
    K --> T["Create a new token<br/>and email the new link"]
    N --> R[/"202 Accepted<br/>If that account exists and isn't verified yet,<br/>we've sent a new link."/]
    T --> R

    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class T ok
    class N trap

How to read it

  1. Three reasons to send nothing: no such account, already verified, or an email was sent less than a minute ago.
  2. Every path ends in the same 202 reply, so attackers can't use this button to find out who has an account.
  3. The cooldown stops attackers from using your app to flood someone's inbox.
  4. Before sending, all old tokens are deleted, so only the link in the newest email works.
