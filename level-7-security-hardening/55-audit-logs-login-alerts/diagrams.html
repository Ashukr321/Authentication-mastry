How to read it

  1. Every attempt, good or bad, becomes an audit entry. None of them contains the password.
  2. Both kinds of failure return the same 401 to the client (topic 51). Only the log knows the reason.
  3. The failure count comes from the audit log itself: the log is your detection data.
  4. On success, the browser's did cookie and the country are compared with Rahul's history.
  5. Yellow boxes send an email to the account owner. The failed-logins email is limited to one per hour.

A known device logging in from home again sends nothing. Alerting on every login teaches users to ignore you.

2. Data flow

Vikram logs in with Rahul's leaked password. Rahul gets the email and throws him out. Real values from our test run.

    C-->>V: 200 + sid cookie
    R->>C: GET /security/not-me?token=M6FVaMJo...
    C-->>R: a page with a form (GET changes nothing)
    R->>C: POST /security/not-me { token, newPassword }
    Note over C: new password, delete ALL 3 sessions, forget 2 devices, token used up
    C->>L: entry 18 password.changed, entry 19 account.secured
    C->>R: Your password was changed (no link)
    V->>C: GET /me/activity (old sid cookie)
    C-->>V: 401 Not signed in ✓

How to read it

  1. Each column is one party. Solid arrows are requests or writes, dashed arrows are replies.
  2. Steps 1–4: guessing fails, but each try is logged and the 5th triggers a heads-up to Rahul.
  3. Steps 5–9: the real password works. Login alerts don't block the attacker; they make sure the owner knows within seconds.
  4. Steps 10–11: the email link only opens a page, because email scanners open links on their own.
  5. Steps 12–15: one POST changes the password and revokes every session, then confirms by email without any link.
  6. Steps 16–17: Vikram's session is gone, and the leaked password no longer works.

With MFA (topic 45), step 5 would have stopped at "enter your code". Alerts are the safety net for accounts that don't have it.

3. Hash chain: why deleting an entry is noticed

Each entry stores the hash of the entry before it. An insider deletes #11 (Vikram's login) straight from the database.

How to read it

  1. hash = sha256(prevHash + the entry as JSON), so each entry depends on all entries before it.
  2. Delete an entry: the next one's prevHash no longer matches.
  3. Edit an entry: its own hash no longer matches its content.
  4. Someone who rewrites the whole chain can recompute every hash, so copy the latest hash somewhere the app can't write, and ship entries to write-once storage.

The demo's POST /demo/tamper plays this insider. Run /admin/audit/verify before and after.
