1. Flow diagram

One POST /login going through every layer of ChaiKart's defense. The cheap checks come first, the password check comes late, and a correct password is still not always enough.

Stopped / safe outcome Attacker wins Counted / watched 
flowchart TD
    A(["POST /login<br/>email + password"]) --> L{"Over the per-IP or<br/>per-account limit?<br/>(topic 16)"}
    L -- Yes --> R429[/"429 Too many attempts"/]
    L -- No --> M{"Site in<br/>attack mode?"}
    M -- No --> P{"Password<br/>correct?"}
    M -- Yes --> T{"Trusted-device cookie<br/>for this email?"}
    T -- Yes --> P
    T -- No --> C{"Fresh, unused<br/>challenge solved?"}
    C -- No --> R403[/"403 challenge required<br/>(password never checked)"/]
    C -- Yes --> P
    P -- No --> F["Count the failure:<br/>per IP, per account, site-wide"]
    F --> R401[/"401 Wrong email or password"/]
    F -. "5 failures in 5 min" .-> ATK["🚨 Attack mode ON<br/>for 15 minutes"]
    P -- "Yes, on /vulnerable/login" --> HIJ[/"200: the bot is inside<br/>Rahul's account"/]
    P -- "Yes, on /login" --> N{"New device AND<br/>(breached password<br/>OR attack mode)?"}

How to read it

  1. Topic 16's limits run first. They stop brute force, but a stuffing bot never trips them.
  2. Every failure is also counted site-wide (yellow). Enough of them flips the whole site into attack mode.
  3. In attack mode, an unknown device must solve a challenge before the password is even looked at. The bot learns nothing.
  4. A trusted-device cookie lets Priya's own laptop skip the challenge.
  5. The right password from a new device, when the password is breached or the site is under attack, still needs the email code.
  6. /vulnerable/login stops at "password correct?": that's where the red box comes from.

Every box was reproduced with curl in the demo, including the red one.

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2: Priya's laptop earns a did cookie on a normal day.
  3. Steps 3–4: five tries, five IPs, five accounts. Topic 16's counters all stay at 1.
  4. Step 5: the site-wide view sees the pattern and switches to attack mode.
  5. Steps 6–11: the bot has to pay CPU for every single guess from now on.
  6. Steps 12–13: the breach check sends only 9998A.
  7. Steps 14–18: the bot holds Rahul's real password and still can't get in. Rahul gets a warning.
  8. Steps 19–20: the real user on a known device notices nothing.

3. Why topic 16 isn't enough

Three password attacks that look alike from far away. Per-account and per-IP counters catch only the first one.

Caught Topic 16's counters stay green What's left for the attacker 
flowchart LR
    BF(["Brute force:<br/>1 account, 1000 passwords"]) --> BF2["Account counter<br/>reaches 5"]
    BF2 --> BF3[/"Locked: per-account lockout ✓"/]
    SP(["Password spraying:<br/>1 common password,<br/>1000 accounts"]) --> SP2["Each account: 1 try<br/>Each IP: a few tries"]
    SP2 --> SP3[/"Common passwords work<br/>for some users"/]
    CS(["Credential stuffing:<br/>1 leaked, REAL password<br/>per account, 1000 IPs"]) --> CS2["Each account: 1 try<br/>Each IP: 1 try"]
    CS2 --> CS3[/"Reused passwords work:<br/>about 0.1% to 2% hit"/]
    SP3 -. fix .-> F1["Breached-password ban<br/>+ site-wide detection"]
    CS3 -. fix .-> F2["Site-wide detection, challenge,<br/>device cookie, email code, MFA"]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class SP3,CS3 error
    class BF3,F1,F2 ok
    class SP2,CS2 trap

How to read it

  1. Brute force hammers one door, so a per-account counter catches it (topic 16).
  2. Spraying tries one weak password everywhere. Banning breached and common passwords removes its ammunition.
  3. Stuffing uses passwords that were really used by those people. Its hit rate is much higher than guessing.
  4. Both spraying and stuffing spread out so every counter sees "1". Only a whole-site view sees the pattern.

1% of a 1-million-line combo list = 10,000 hijacked accounts, with no single counter ever going red.

4. k-anonymity: checking a password without sending it

How the signup check finds out that a password is in a breach list, while the API learns only 5 hash characters. Real values from the demo.

sequenceDiagram
    autonumber
    actor U as Amit (signing up)
    participant A as ChaiKart server
    participant P as Pwned Passwords API

    U->>A: POST /signup { password: "Password@123" }
    Note over A: sha1 = 25C2C | 9AFDD83B8D34234AA2881CC341C09689AAA
    A->>P: GET /range/25C2C (Add-Padding: true)
    Note over P: sees only 25C2C, shared by hundreds of different passwords
    P-->>A: 11 lines: 1555A896…:0, 2504DB29…:0, … 9AFDD83B…:120000, …
    Note over A: looks for 9AFDD83B… locally: found, count 120000
    A-->>U: 400 "This password has appeared in 1,20,000 data breaches"
    U->>A: POST /signup { password: "auto-rickshaw-at-midnight" }
    A->>P: GET /range/1D775
    P-->>A: 10 lines, all padding (count 0)
    A-->>U: 201 Account created

How to read it

  1. Step 2: the password is hashed with SHA-1 only for this lookup. It's still stored with scrypt.
  2. Step 3: the first 5 characters go out. The other 35 never leave the server.
  3. Step 5: the API answers with every suffix for that prefix, plus fake :0 padding lines, so it can't tell which one you wanted.
  4. Step 6: the match happens on your server.
  5. Steps 8–11: a unique passphrase has no match, only padding.

Run the same check at password change and reset too, not just signup.
