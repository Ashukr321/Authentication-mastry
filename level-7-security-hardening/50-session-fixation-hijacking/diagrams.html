1. Flow diagram

Every check a session id passes through on ChaiCart's safe routes. Fixation is stopped at login; hijacking is made hard and short-lived.

Safe outcome Attacker wins (vulnerable route) Only a signal: can be faked 
flowchart TD

    B -- "URL: ?sid=" --> E1[/"Vulnerable: adopted as the cookie<br/>fixation by a link"/]
    B -- "Cookie" --> C{"Did WE issue it?<br/>sha256 found in sessions"}
    C -- No --> OK1[/"Ignored: fresh random id issued"/]
    C -- Yes --> D{"Idle 30 min or<br/>12 h since login?"}

    D -- No --> F{"Logged in from<br/>the same browser?"}

    F -- "Yes (or UA copied)" --> G["Request allowed"]
    G --> H{"Logging in now?"}
    H -- "Safe: POST /login" --> OK4[/"Old id deleted, NEW id issued,<br/>cart copied over"/]
    H -- "Vulnerable: same id kept" --> E2[/"Whoever knew the id<br/>is now logged in too"/]

How to read it

  1. Ids come from the cookie only, and only ids the server issued count. That alone stops "made-up id in a link".
  2. Timeouts are checked on the server. The cookie's own expiry doesn't matter: the attacker controls his copy.
  3. The browser check (yellow) catches a careless thief, but a careful one copies the User-Agent. It's a signal, not a lock.
  4. At login the id is replaced. This is the fixation fix: the id the attacker knows dies right there.
  5. Dangerous actions ask for the password, and a password change ends every session, including ones you don't know were stolen.

Every box here was hit in the demo's curl run in the README.

2. Data flow: fixation

Vikram plants a session id, Rahul logs in. Vulnerable login on top, safe login below, with the real session tags from our run.

sequenceDiagram
    autonumber
    actor V as Vikram
    participant B as Rahul's browser
    participant S as ChaiCart (localhost:3050)

    Note over V,S: ❌ Vulnerable routes
    V->>S: GET /vulnerable/shop?sid=vikram-chose-this-id-123
    S-->>V: 200 session 443088c0 (made-up id adopted)
    V->>B: "Great chai deals!" link with ?sid=vikram-chose-this-id-123
    B->>S: GET /vulnerable/shop?sid=vikram-chose-this-id-123
    S-->>B: Set-Cookie sid=vikram-chose-this-id-123 (no HttpOnly)
    B->>S: POST /vulnerable/login (Rahul's password)
    S-->>B: 200 Logged in, session 443088c0 (SAME id)
    V->>S: GET /vulnerable/me (cookie sid=vikram-chose-this-id-123)
    S-->>V: 200 email Rahul's, cart Masala chai x2 😱

    Note over V,S: ✅ Safe routes
    V->>S: GET /shop (no cookie)
    S-->>V: Set-Cookie sid=Hhz0k3… (HttpOnly), session 82f26286
    Note over B: the cookie is planted in Rahul's browser (subdomain, shared PC)
    B->>S: POST /login with cookie sid=Hhz0k3…
    Note over S: delete 82f26286, create a new id, copy the cart
    S-->>B: Set-Cookie new sid, oldSession 82f26286, session f69d5357
    V->>S: GET /me (cookie sid=Hhz0k3…)
    S-->>V: 401 Not signed in ✓

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2: the permissive server accepts an id nobody issued. Vikram didn't even need a real one.
  3. Steps 3–5: one click and Rahul's browser carries Vikram's id.
  4. Steps 6–7: the login upgrades the same session. Look at the tag: 443088c0 before and after.
  5. Steps 8–9: Vikram is Rahul. No password, no theft.
  6. Steps 10–15: even with a planted cookie, the safe login throws the old id away. Vikram's copy is worthless.

3. Data flow: hijacking

Rahul's id leaks after login. What each defense does to Vikram's copy.

sequenceDiagram
    autonumber
    actor V as Vikram
    participant B as Rahul's browser
    participant S as ChaiCart (localhost:3050)

    Note over B,V: Rahul's sid leaks (log file, XSS, open Wi-Fi)
    V->>S: GET /vulnerable/me (Rahul's sid, UA Vikram-PC)
    S-->>V: 200 email Rahul's 😱 (no checks)
    V->>S: GET /me (Rahul's sid, UA Vikram-PC)
    Note over S: logged in from Rahul-Laptop-Chrome, now Vikram-PC
    S-->>V: 401, session f69d5357 deleted
    S-->>B: email to Rahul "we signed you out"
    B->>S: POST /login again, session a6baa358
    Note over B,V: leaks again, Vikram copies the UA too
    V->>S: GET /me (Rahul's sid, UA Rahul-Laptop-Chrome)
    S-->>V: 200 (the browser signal was faked)
    V->>S: POST /account/password, wrong current password
    S-->>V: 403 Confirm with your current password ✓
    B->>S: POST /account/password, correct current password
    Note over S: delete ALL of Rahul's sessions (2), new id for this browser
    S-->>B: 200 sessionsEnded 2, session 9ca51ce5
    V->>S: GET /me (old sid)
    S-->>V: 401 Not signed in ✓

How to read it

  1. Steps 1–2: the vulnerable route trusts any copy, forever.
  2. Steps 3–5: the safe route notices a different browser and ends the session for both sides. Rahul is told.
  3. Steps 7–8: a careful thief copies the User-Agent too, and gets in. That's why binding is only one layer.
  4. Steps 9–10: the cookie alone can't change the password. A thief has the cookie, not the password.
  5. Steps 11–14: Rahul's password change ends every session (including the fixated one from section 2), so every stolen copy dies at once.

Not shown: the idle (30 min) and absolute (12 h) timeouts end a stolen session even if nobody notices the theft.
