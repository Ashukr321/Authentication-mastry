1. Flow diagram

What the PaisaPay API does with a cross-origin request that carries Rahul's cookie, and what the browser then does with the answer.

Allowed / safely refused Error Careful: the server still answers, the browser decides 
flowchart TD
    A(["Request from another origin<br/>Origin header + cookie sid"]) --> V["Always set Vary: Origin"]
    V --> Q{"Origin exactly in<br/>ALLOWED_ORIGINS?"}
    Q -- Yes --> H["ACAO: that exact origin<br/>Allow-Credentials: true"]
    Q -- No --> N["No CORS headers"]
    H --> P1{"OPTIONS preflight?"}
    P1 -- Yes --> OK1[/"204 + Allow-Methods: GET, POST<br/>Allow-Headers: Content-Type<br/>Max-Age: 600"/]
    P1 -- No --> OK2[/"200 + data:<br/>the page can read it"/]
    N --> P2{"What kind of request?"}
    P2 -- "OPTIONS preflight" --> OK3[/"204, no headers:<br/>browser never sends the real request"/]
    P2 -- "GET" --> T[/"200 + data, but the browser<br/>hides it from the page"/]
    P2 -- "POST / PUT / DELETE" --> E1[/"403 Origin is not allowed<br/>(CSRF check, topic 47)"/]

How to read it

  1. Vary: Origin goes on every response, because the headers depend on who asked.
  2. The only decision is an exact allow-list match. Yes → the origin is echoed back with Allow-Credentials: true.
  3. A non-allowed preflight gets no headers, so the browser never sends the JSON POST.
  4. The yellow box: for a GET, the server still sends the data. The browser hides it from the page. curl would see it all.
  5. Writes from other origins are refused by an Origin check, because CORS alone doesn't stop a request from being sent.

Never * with credentials: the browser rejects it. The fix is the exact allow-list, not reflecting the Origin.

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–4: the frontend is on another site, so the cookie is SameSite=None; Secure and the API allow-lists its exact origin.
  3. Steps 5–9: a JSON POST triggers a preflight. Only after it passes does the browser send the real POST.
  4. Steps 10–13: the browser does send Rahul's cookie for Vikram's page, and the API does answer, but with no CORS headers the browser hides the data.
  5. Steps 14–17: the reflecting endpoint hands Vikram's origin the permission, and his page posts the data to his own server.
  6. Steps 18–22: with the preflight passing too, a CORS bug becomes a money-moving bug, not just a data leak.

3. Allow-list bugs

The same attacker origin against different ways of writing the Origin check. Only one of them says no.

How to read it

  1. Every red result is a real-world bug pattern. The demo has reflect, prefix and null as routes you can try.
  2. String tricks (prefix, suffix, includes, regex) all fail because an attacker can register a domain that matches.
  3. null sounds like "nobody", but any page can produce it with a sandboxed <iframe>.
  4. The fix is boring on purpose: a Set of full origins (scheme + host + port) and .has().

Even a perfect allow-list trusts every page on those origins. An XSS on an allowed origin (topic 48) gets full access.
