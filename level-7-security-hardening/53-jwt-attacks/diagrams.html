1. Flow diagram

How to read it

  1. The header (yellow) was written by whoever made the token. Every attack starts by editing it.
  2. The vulnerable verifier asks the header three questions: is it signed? (alg), which key? (kid, jku), which algorithm? (alg). Each answer is a way in.
  3. The safe verifier asks only one thing: which of OUR keys (kid in a fixed map). Key and algorithm come from that map.
  4. Even a good signature isn't enough: exp, iss and aud must be checked too (topic 27).

Attack 5 (weak secret) isn't on this chart: there the verifier is correct, and the attacker simply knows the secret. See diagram 3.

2. Data flow

Algorithm confusion, with the real headers from the demo. The same forged token goes to both verifiers.

sequenceDiagram
    autonumber
    actor V as Vikram (normal user)
    participant E as Vikram's server (127.0.0.1:3154)
    participant A as ChaiCart API (localhost:3153)

    V->>A: POST /login (Vikram's own account)
    A-->>V: 200 token: header alg RS256, kid rs-1 / payload role user
    V->>A: GET /admin (Bearer his real token)
    A-->>V: 403 Admins only
    V->>E: POST /forge/confusion { token, claims: { role: admin } }
    E->>A: GET /.well-known/jwks.json
    A-->>E: { keys: [ RSA public key, kid rs-1 ] } (public on purpose)
    Note over E: header becomes alg HS256, kid rs-1 / payload role admin
    Note over E: signature = HMAC-SHA256(public key PEM, header.payload)
    E-->>V: forged token
    V->>A: GET /vulnerable/admin (Bearer forged)
    Note over A: header says HS256, so HMAC with PUBLIC_KEY: it matches
    A-->>V: 200 Welcome to the admin panel 😱
    V->>A: GET /admin (Bearer forged)
    Note over A: kid rs-1 means RS256 only (pinned)
    A-->>V: 401 Invalid token (log: invalid algorithm) ✓

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–4: Vikram is a real user with a real token. He just isn't an admin.
  3. Steps 6–7: he downloads our public key. Nothing was stolen: JWKS is meant to be public.
  4. Notes after step 7: he changes alg to HS256 and uses the public key text as an HMAC secret.
  5. Steps 11–13: the vulnerable verifier lets the header pick HMAC, computes it with the same public key, and gets the same answer.
  6. Steps 14–16: the safe verifier knows rs-1 is an RS256 key and refuses any other algorithm.

Swap confusion for none, kid or jku in step 5 and the shape is the same: vulnerable says 200, safe says 401.

3. Weak secret: the attack that needs no bug

✅ Random secret, or no shared secret

How to read it

  1. The loop (yellow) runs offline. Your server never sees a single guess, so rate limits, lockouts and alerts can't help.
  2. hashcat runs billions of these HMACs per second on a GPU. A human-chosen secret falls in seconds.
  3. Right side: 32 random bytes can't be guessed, and asymmetric algorithms have no shared secret at all.

A cracked or leaked secret means every token signed with it is suspect. Rotate it (topic 54).
