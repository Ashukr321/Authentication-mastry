1. Flow diagram

One login request on the safe app, and the cheat-sheet rule that guards each step. The red boxes are what the legacy app does instead.

Cheat sheet followed Legacy app: rule broken Careful: easy to get subtly wrong

    A(["POST /login<br/>email + password"]) --> H["Headers on every response:<br/>no-store, nosniff, frame-ancestors<br/>(HTTP Headers CS)"]
    H --> C{"Cross-site request?<br/>(CSRF CS)"}
    C -- "Yes" --> C1[/"403 refused"/]
    C -- "No" --> R{"5+ failures for this email<br/>in 15 min? (Authentication CS)"}

How to read it

  1. Follow the solid arrows top to bottom: that's the safe app. Each box names the cheat sheet (CS) behind it.
  2. The dotted arrows to red boxes show what the legacy app does at the same step.
  3. The rate limit runs before the expensive hash, so a flood of guesses doesn't burn 128 MiB each.
  4. The yellow box is the subtle part: if only real accounts got a 429, the rate limiter itself would reveal who has an account.
  5. The success path ends with a brand-new session id. Reusing the guest id is session fixation (topic 50).

The auditor checks every box here over real HTTP: run /audit/safe and /audit/legacy.

    A->>L: GET / (guest)
    L-->>A: Set-Cookie connect.sid=sess-1001 (no flags) ❌
    A->>L: POST /login (Cookie sess-1001)
    L-->>A: 200, no new cookie: still sess-1001 ❌ fixation
    A->>L: POST /transfer ₹5000 (Origin: evil.example)
    L-->>A: 200 Sent ₹5000 to vikram ❌ CSRF
    A->>L: POST /logout, then GET /me with the old cookie
    L-->>A: 200 balance ₹12,500 ❌ session still alive
    A->>L: POST /login x10 with wrong passwords
    L-->>A: 401, 401, 401 … never 429 ❌
    A-->>P: text report: Score 0/16

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 2–5: signing up twice shows whether "this email has an account" leaks.
  3. The note after step 5 is the one white-box check: the auditor reads how the password was stored. Everything else is black-box HTTP.
  4. Steps 6–9: unknown email vs wrong password must look identical.
  5. Steps 10–13: the guest id must change at login. Here it doesn't.
  6. Steps 14–17: a cross-site transfer and a reused cookie after logout both work. Two serious bugs.
  7. The brute-force check runs last, because on a safe app it locks the test account.

The same run against the safe app ends with "Score: 16/16" (README, step ②).

How to read it

  1. The Top 10 tells you which risks matter, ASVS turns them into requirements, WSTG says how to test them. All three point to the cheat sheets for the "how to build it" part.
  2. Each cheat sheet in the middle is a short page you open while building that feature.
  3. The green boxes are where this course implements those rules, with a working server.js.
  4. This topic's auditor checks rules from the first four rows plus headers, CSRF and error handling.

You don't need to memorise the cheat sheets. Know which one exists for the feature in front of you, and open it.
