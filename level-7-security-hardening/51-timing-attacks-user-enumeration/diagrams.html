How to read it

  1. The message is the obvious leak (red). Topics 06, 07 and 13 already fixed it.
  2. The yellow boxes are the sneaky ones: the message is perfect, but the stopwatch still tells the truth.
  3. Skipping the slow password hash for unknown emails is the classic login timing leak. Fix: hash against a dummy hash.
  4. Waiting for an email before replying is the classic forgot-password leak. Fix: reply first, send later.
  5. Rate limits don't remove a difference, but they make measuring it take forever.

Every yellow and red box was measured with curl in the demo: /vulnerable/login and /vulnerable/forgot-password.

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies, with the real time curl measured.
  2. Steps 1–6: the vulnerable login leaks twice: the message and the time.
  3. Steps 7–12: the safe login gives the same reply and does the same scrypt work. The small wobble in time is machine load, not a pattern.
  4. Steps 13–18: the leaky compare gets slower with every correct leading character, so Vikram finds the key one character at a time.
  5. Steps 19–20: timingSafeEqual on SHA-256 hashes takes the same time no matter how close the guess is.

3. Leaky vs safe compare

Why === leaks and timingSafeEqual doesn't. The secret is 4d0fe2; the guess is 4d9xxx.

Time depends on the guess Time is always the same

    C1 --> C2["char 2: d = d, continue"]

flowchart TD
    A2(["timingSafeEqual(sha256(guess), sha256(secret))"]) --> H["Both are 32 bytes:<br/>length can't leak"]
    H --> ALL["Check all 32 bytes,<br/>never stop early"]
    ALL --> R[/"Same time for every guess:<br/>nothing to measure"/]

    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    class R,H ok

How to read it

  1. Left: a normal string compare stops at the first difference. More correct leading characters = more work = more time.
  2. Even the length check leaks: a wrong length returns faster than the right one.
  3. Right: hashing both sides makes them the same length, and timingSafeEqual always looks at every byte.
  4. Real === leaks nanoseconds, not 40 ms like our demo, but attackers average thousands of requests to see it.

Use it for API keys, HMAC webhook signatures, CSRF tokens and OTP codes. For passwords, compare the hashes (scrypt/bcrypt/argon2), never the passwords.
