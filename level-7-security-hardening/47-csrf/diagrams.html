1. Flow diagram

Every check a request to POST /transfer passes before PaisaPay moves money. The cheap header checks run first, the token check last.

Success Error: the server stops here Careful step: the browser decides, not your code 
flowchart TD
    A(["POST /transfer<br/>to=vikram, amount=5000"]) --> C{"Browser: attach the sid cookie?<br/>(SameSite=Lax)"}
    C -- "Cross-site POST: no cookie" --> N[/"401 Not signed in"/]
    C -- "Same-site or same-origin: cookie sent" --> F{"Sec-Fetch-Site is<br/>same-origin or none?"}
    F -- "No: same-site / cross-site" --> E1[/"403 request came from another site"/]
    F -- "Yes, or header missing" --> O{"Origin missing or<br/>exactly our BASE_URL?"}
    O -- No --> E2[/"403 Origin is not ours"/]
    O -- Yes --> S{"Valid session?"}
    S -- No --> N
    S -- Yes --> T{"_csrf field or X-CSRF-Token<br/>equals session.csrfToken?<br/>(timingSafeEqual)"}
    T -- "No / missing" --> E3[/"403 missing or wrong CSRF token"/]
    T -- Yes --> V{"Amount valid,<br/>recipient exists,<br/>enough balance?"}
    V -- No --> E4[/"400"/]
    V -- Yes --> OK[/"200 Sent ₹5000"/]

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class N,E1,E2,E3,E4 error
    class OK ok
    class C trap

How to read it

  1. The yellow box happens in the browser: SameSite=Lax keeps the cookie off cross-site POSTs. A same-site attacker (a subdomain, another port) still gets it attached.
  2. Sec-Fetch-Site is the check that refuses those same-site attackers.
  3. Origin must be an exact match with our own configured origin. null is refused.
  4. The CSRF token is the last word: a forged form never has it, because the attacker can't read our pages.
  5. Only then does the business logic (amount, balance) run.

curl sends no Origin or Sec-Fetch-Site, so it passes the header checks. It still needs the token. That's why the token is the layer that always runs.

2. Data flow

Rahul is logged in to PaisaPay and opens Vikram's "you won a prize" page in another tab. Real headers from our test run.

sequenceDiagram
    autonumber
    actor U as Rahul
    participant B as Rahul's browser
    participant P as PaisaPay (localhost:3047)
    participant E as Vikram's page (localhost:3048)

    U->>B: Logs in as Rahul
    B->>P: POST /login { email, password }
    Note over P: new session { email, csrfToken: "aIXI…BIs" }
    P-->>B: Set-Cookie: sid=SkqI… (HttpOnly, SameSite=Lax)
    B->>P: GET /
    P-->>B: Home page with a hidden field _csrf=aIXI…BIs
    U->>B: Sends ₹100 with the real form
    B->>P: POST /transfer to, amount, _csrf=aIXI… (cookie sid, Origin: localhost:3047, Sec-Fetch-Site: same-origin)
    P-->>B: 200 Sent ₹100 ✓
    U->>E: Opens the prize page
    E-->>B: Page with a hidden form (to=vikram, amount=5000, NO token)
    B->>P: fetch /api/csrf-token (trap D)
    P-->>B: { csrfToken } but no CORS header
    Note over B: Response hidden from Vikram's page: Failed to fetch
    U->>B: Presses "Claim prize"
    B->>P: POST /transfer to=vikram, amount=5000 (cookie sid sent: same-site! Origin: localhost:3048, Sec-Fetch-Site: same-site)
    Note over P: Sec-Fetch-Site is not same-origin
    P-->>B: 403 CSRF check failed
    Note over P: Same form to /vulnerable/transfer (cookie only)
    P-->>B: 200 Sent ₹5000 to vikram 😱

How to read it

  1. Each column is one party. Solid arrows are requests, dashed arrows are replies.
  2. Steps 2–5: the token lives in the session and in our own page only.
  3. Step 7: the real form carries the token, and the browser says same-origin.
  4. Steps 11–12: Vikram's script tries to read the token. The request even reaches the server, but the browser hides the reply from his page.
  5. Step 14: the forged form does carry Rahul's cookie (ports don't make a different site), but it has no token and the browser labels it same-site.
  6. Steps 15–16: the protected route refuses; the cookie-only route pays.

3. Which defense stops what

Left: an attacker on a different site (127.0.0.1:3048). Right: an attacker on the same site (localhost:3048, like a hacked subdomain). Both aim at PaisaPay on localhost:3047.

How to read it

  1. SameSite=Lax only helps on the left (other sites), and only for POST. Link clicks (GET) still carry the cookie, so never change data on GET.
  2. On the right, SameSite does nothing: localhost:3047 and localhost:3048 are the same site, just like paisapay.in and blog.paisapay.in.
  3. The protected /transfer is safe on both sides: Fetch Metadata, the exact Origin check and the token don't care about "site".
  4. The token stays secret because the attacker can't read our responses. A CORS config that allows it (topic 49) or an XSS on our own page (topic 48) would break that.

Every red box is the /vulnerable/transfer route: it trusts the cookie alone and accepts GET. The same request to /transfer is refused every time.
