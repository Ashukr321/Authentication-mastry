1. Flow diagram

How PaisaVault checks a JWT against its key ring, and how a signing-key rotation moves through it. Planned rotation logs nobody out; an emergency one logs out everyone holding a token from the leaked key, on purpose.

Accepted / safe Rejected (401 / refused) Careful: the overlap window 
flowchart TD
    BOOT(["Server starts"]) --> S{"ADMIN_TOKENS set<br/>and 32+ chars?"}
    S -- No --> X0[/"Refuse to start:<br/>fail fast"/]
    S -- Yes --> REQ(["Request with a JWT"])
    REQ --> A{"header alg<br/>is EdDSA?"}
    A -- "No: none / HS256" --> X1[/"401 Unexpected alg"/]
    A -- Yes --> K{"kid found in<br/>OUR key ring?"}
    K -- "No: retired or made up" --> X2[/"401 Unknown or<br/>retired signing key"/]
    K -- "sig-1: verify-only" --> W["Old token, still valid<br/>during the overlap"]
    K -- "sig-2: current" --> V
    W --> V{"Signature OK<br/>and not expired?"}
    V -- No --> X3[/"401"/]
    V -- Yes --> OK[/"200: request served"/]
    W -. "after 15 min (planned)<br/>or NOW (key leaked)" .-> R["Admin retires sig-1"]
    R -.-> X2

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class X0,X1,X2,X3 error
    class OK ok
    class W,R trap

How to read it

  1. Boot: a missing or weak secret stops the server at once, instead of failing quietly in production.
  2. The algorithm is pinned before any key is touched, so alg: none never gets further (topic 53).
  3. The kid only selects a key from our own ring. An unknown kid is a 401, never a lookup somewhere else.
  4. After a rotation, the old key is verify-only (yellow): old tokens keep working, new tokens use the new key.
  5. Retiring the old key (dashed) sends its tokens to the red box: after one token lifetime in a planned rotation, or immediately if it leaked.

The current key can't be retired. The demo answers 409 Rotate first, then retire it.

2. Data flow

Rotating the key that encrypts Rahul's PAN, with the real values from our test run on port 3054.

sequenceDiagram
    autonumber
    actor R as Rahul
    actor A as Admin
    participant P as PaisaVault
    participant D as Database row

    R->>P: PUT /api/me/pan { pan: "ABCDE1234F" }
    P->>D: { keyId: "data-1", iv, tag, ciphertext: "Y9t7V1bNoUy/TA==" }
    P-->>R: 200 { encryptedWith: "data-1" }
    A->>P: POST /admin/data-keys/rotate
    P-->>A: 200 new writes use data-2, 1 row still uses data-1
    R->>P: GET /api/me/pan
    Note over P: row says data-1, so decrypt with data-1 (now decrypt-only)
    P-->>R: 200 { pan: "******234F", encryptedWith: "data-1" }
    A->>P: DELETE /admin/data-keys/data-1
    P-->>A: 409 1 row still encrypted with data-1, or that data is lost
    A->>P: POST /admin/data-keys/reencrypt
    P->>D: decrypt with data-1, encrypt with data-2: { keyId: "data-2", ... }
    P-->>A: 200 Re-encrypted 1 row(s) with data-2
    A->>P: DELETE /admin/data-keys/data-1
    P-->>A: 200 data-1 retired, no data used it ✓

How to read it

  1. Each column is one party. Solid arrows are requests or writes, dashed arrows are replies.
  2. Step 2: the row stores the key ID next to the ciphertext. The PAN itself is never stored.
  3. Steps 4–8: after rotation, old rows still open, because each row names its own key.
  4. Steps 9–10: deleting a key that still has rows is refused. Without that key the PAN could never be read again.
  5. Steps 11–15: re-encrypt first, then retire. That's the whole recipe.

In a KMS setup (envelope encryption), step 12 re-wraps a small data key instead of re-encrypting every row.

3. Key lifecycle

Every key, signing or encryption, moves through the same states. Rotation is just a new key entering on the left while the old one moves right.

Normal path Emergency path Overlap: old and new both work 
flowchart LR
    G(["Generated in KMS /<br/>secrets manager"]) --> PUB["Published<br/>(in JWKS, not signing yet)"]
    PUB --> CUR["Current<br/>signs / encrypts"]
    CUR -- "rotation" --> OLD["Verify-only /<br/>decrypt-only"]
    OLD -- "tokens expired /<br/>rows re-encrypted" --> RET[/"Retired: destroyed"/]
    CUR -. "key leaked" .-> EM["Rotate now +<br/>retire immediately"]
    EM -.-> RET

    classDef error fill:#fee2e2,stroke:#dc2626,color:#7f1d1d
    classDef ok fill:#dcfce7,stroke:#16a34a,color:#14532d
    classDef trap fill:#fef9c3,stroke:#ca8a04,color:#713f12
    class G,PUB,CUR,RET ok
    class OLD trap
    class EM error

How to read it

  1. Published first: verifiers cache the JWKS, so the new public key should be there before any token uses it.
  2. Current: exactly one key signs new tokens or encrypts new data.
  3. Verify/decrypt-only (yellow) is the overlap that makes rotation painless: nothing breaks.
  4. Retired only when nothing depends on it: no unexpired tokens, no rows.
  5. The emergency path (red) skips the overlap. Users log in again; data keys still need re-encryption first.

Shared secrets (admin tokens, webhook secrets) follow the same idea with two values: ADMIN_TOKENS=old,new, then just new.
